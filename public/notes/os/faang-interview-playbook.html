question 1: "what happens when you type 'ls -l' in a shell and press enter?"

The legendary systems interview question. Here is the complete end-to-end trace from keystroke to terminal output:

Step-by-Step Execution Journey

  1. Keystroke & Interrupt: When you press Enter, the keyboard controller raises a hardware interrupt. The CPU transitions to Ring 0, where the kernel keyboard driver delivers the ASCII newline \n through the terminal line discipline to the waiting shell process.
  2. Shell Processing: The shell (e.g. bash), which was blocked in a read(0, ...) system call, wakes up. It tokenizes the input string into ["ls", "-l"] and searches the $PATH environment variable for the executable binary /bin/ls.
  3. Process Creation (fork): The shell executes the fork() system call. The kernel duplicates the shell's task_struct and page tables using Copy-On-Write (COW). The child process is assigned a new PID.
  4. Program Replacement (execve): The child process calls execve("/bin/ls", ["ls", "-l"], envp). The kernel:
    • Discards the child's existing memory space (code, stack, heap).
    • Parses the ELF (Executable and Linkable Format) binary header of /bin/ls.
    • Sets up new virtual memory segments (Text, Data, BSS, Stack).
    • Invokes the dynamic linker (ld.so) to map required shared libraries (like libc.so) via mmap().
  5. Directory Traversal: The ls program invokes openat(AT_FDCWD, ".", O_RDONLY) followed by getdents64() to read raw directory entries from the filesystem. It calls lstat() on each entry to fetch Inode metadata (permissions, owner UID, file size, timestamps).
  6. Output & Zero-Copy Rendering: ls formats the text in user space and calls write(1, formatted_string, len). The kernel streams the bytes to the pseudo-terminal device buffer.
  7. Exit & Reap: ls executes exit_group(0). The kernel frees its memory and marks its PCB as EXIT_ZOMBIE, sending a SIGCHLD signal to the parent shell. The shell, which was waiting via waitpid(), reads the return code 0, reaps the child, and prints the next prompt.

question 2: "what actually happens during malloc(100) vs malloc(100MB)?"

One of the most frequently failed interview questions. Candidates assume malloc() is a system call. It is not! malloc() is a user-space C library function that manages memory pools using two distinct kernel syscalls:

Allocation SizeMechanism UsedKernel SyscallBehavior
Small Allocations (< 128 KB) Expands the process Heap Segment brk() / sbrk() Moves the heap break pointer upwards. To avoid syscall overhead, the user-space allocator (jemalloc/glibc) requests memory in chunks (e.g. 64KB) and carves it up in user space using arena bins.
Large Allocations (≥ 128 KB) Allocates a private Anonymous Memory Map mmap(MAP_ANONYMOUS | MAP_PRIVATE) Creates a brand-new Virtual Memory Area (VMA) outside the heap. When free() is called, memory is instantly unmapped and returned to the OS kernel via munmap().
⚠️ the punchline: virtual vs physical allocation
If you execute char *buf = malloc(100 * 1024 * 1024); (100 Megabytes):
How much physical RAM was allocated? ZERO BYTES!
The kernel merely creates a 100MB Virtual Memory Area (VMA) in the process's page table with all PTE Present Bits set to 0. Physical RAM frames are only committed one 4KB page at a time when your program actively writes to an address, triggering a hardware Page Fault!

the 60-second linux production server triage

When an on-call incident fires and a production server is unresponsive, do not randomly guess. Run this 8-step triage sequence:

  1. uptime: Check load averages (1 min, 5 min, 15 min). If load average is higher than the number of CPU cores, processes are queued up waiting.
  2. dmesg -T | tail -50: Always check this first! Look for hardware errors, TCP SYN floods, or the Linux kernel OOM Killer murdering your database (look for "Out of memory: Kill process...").
  3. top or htop: Look at the CPU summary line:
    • High %us (User): Application bottleneck (infinite loop, inefficient JSON parsing, regex catastrophe).
    • High %sy (System): Kernel bottleneck (too many syscalls, lock contention, futex storms).
    • High %wa (I/O Wait): Disk or network bottleneck (slow SSD, saturated swap space).
  4. vmstat 1 5: Check the r column (runnable tasks waiting for CPU) and si/so (swap-in/swap-out). If si/so is non-zero, your machine is thrashing RAM to disk!
  5. iostat -xz 1 5: Inspect %util (disk saturation) and await (average I/O latency in ms). If %util > 95%, disk I/O is saturated.
  6. free -m: Check available memory (RAM + buffer/cache). Remember: high cache usage is good; low available RAM is bad.
  7. perf top: Profiles CPU cycles in real time down to the exact C function. Instantly reveals whether CPU time is spent in your app, glibc, or kernel locks.
  8. strace -c -p <PID>: Attaches to the slow process and outputs a histogram of all system calls and total time spent in the kernel.

system design: architecting a starvation-free reader-writer lock

Standard reader-writer locks prioritize readers, allowing an endless stream of incoming reads to completely starve writers. In systems design interviews, you will be asked how to design a fair, starvation-free lock:

State VariableRole in Coordination
active_readersCount of threads currently reading shared memory.
writer_activeBoolean flag indicating whether a writer is actively modifying data.
waiting_writersCount of writers waiting in the queue. The anti-starvation key!
  • Read Lock Protocol: An incoming reader must wait if a writer is active OR if any writers are already waiting in line (waiting_writers > 0). This single check cuts off the reader cascade and prevents writer starvation! Once clear, increment active_readers.
  • Read Unlock Protocol: Decrement active_readers. If count reaches zero, signal the condition variable to wake up a waiting writer.
  • Write Lock Protocol: Increment waiting_writers to register place in line. Sleep until writer_active == false AND active_readers == 0. Once awake, decrement waiting_writers and set writer_active = true.
  • Write Unlock Protocol: Clear writer_active = false and broadcast to wake up the next queued threads (readers or writers).

quick check

  • Does `malloc(1GB)` commit 1GB of physical RAM immediately? No. It only creates a virtual memory mapping. Physical frames are allocated on demand via page faults on first write.
  • Which command allows you to inspect live system calls made by a running process? strace -p <PID>.
  • Why does high `%wa` in `top` indicate an I/O bottleneck? Because CPU cores are sitting idle waiting for outstanding disk or network I/O requests to complete.

the 20-second summary

FAANG systems interviews evaluate your ability to connect code to kernel mechanics and hardware physics. Commands like ls -l trace the complete path from terminal interrupts through fork, execve, ELF parsing, and VFS Inode traversal. Memory allocators balance fast user-space arenas with lazy virtual demand paging, and production incident response demands systematic command line triage (uptime $\to$ dmesg $\to$ top $\to$ vmstat $\to$ iostat $\to$ perf).
