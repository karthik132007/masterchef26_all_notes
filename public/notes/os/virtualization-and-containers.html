demystifying the cloud stack — hypervisors, linux namespaces, cgroups, and overlayfs.

the 30-second elevator pitch

There is a massive misconception in the software industry: "A Docker container is a lightweight virtual machine." This is completely false. A container is just a regular Linux process running on the host kernel, restricted by two kernel features: Namespaces (which control what it can see) and Cgroups (which control what it can use).

  • The Hotel vs Apartment Analogy:
    • Virtual Machine (VM): A standalone house. It has its own private plumbing, electrical wiring, HVAC, and foundation (Guest OS kernel, virtual drivers, BIOS). Completely secure and isolated, but heavy to build and heat.
    • Container: An apartment in a large complex. All tenants share the same foundation and central plumbing (the single shared Linux Host Kernel), but your front door has a lock, your windows have blinds (Namespaces), and your breaker box limits you to 15 amps (Cgroups).
🧷 the two pillars of containerization
1. Namespaces (Isolation): What a process can SEE (its view of PIDs, network cards, mounts, users).
2. Control Groups / Cgroups (Resource Limiting): What a process can USE (CPU percentage, RAM megabytes, I/O bandwidth, max processes).

the 7 linux namespaces (what a container sees)

When you run docker run, the container runtime invokes the clone() system call with namespace flags:

NamespaceSyscall FlagWhat It Isolates
PIDCLONE_NEWPIDProcess IDs. The entrypoint process becomes PID 1 inside the container, while on the host it is regular PID 28401! Cannot see or kill host processes.
NETCLONE_NEWNETNetwork devices, IP addresses, IP routing tables, port bindings, firewall rules.
MNTCLONE_NEWNSFilesystem mount points. Isolates the container root filesystem from the host.
UTSCLONE_NEWUTSHostname and NIS domain name (e.g. my-container-pod).
IPCCLONE_NEWIPCInter-process communication (POSIX message queues, System V shared memory).
USERCLONE_NEWUSERUser & Group IDs. Root (UID 0) inside container maps to non-privileged user (UID 10001) on host!
CGROUPCLONE_NEWCGROUPIsolates the view of the cgroup hierarchy.

control groups (cgroups v2): resource boundaries

If Namespaces give a process its own world, Cgroups (Control Groups) prevent that world from devouring the entire physical server:

  • CPU Quotas (CFS Bandwidth Control):

    In Kubernetes, setting a CPU limit of 0.5 cores configures cpu.max to 50000 100000 (meaning a 50ms execution quota per 100ms cycle). Every 100ms period, this container is strictly allowed to run for at most 50ms. If it attempts to compute beyond that threshold, the Linux CFS scheduler throttles the process, causing severe latency spikes!

  • Memory Limits & OOM:

    Setting resources.limits.memory: "512Mi" writes to memory.max. If the application allocates 513MB, the kernel's memory controller immediately delivers an OOMKilled event (Exit Code 137), terminating the container instantly.

  • PID Limits (Anti-Fork-Bomb):

    Setting pids.max = 100 prevents a malicious script (:(){ :|:& };:) from spawning 100,000 processes and freezing the cloud server.

how docker images work: union filesystems & overlayfs

If you run 50 containers running node:18 (each 1 GB in size), does your server consume 50 GB of disk space? No! It consumes only 1 GB. This is made possible by OverlayFS:

  1. LowerDir (Read-Only): The layers built during docker build. Stored once on disk and shared in read-only memory across all containers.
  2. UpperDir (Read-Write): A tiny, ephemeral scratch directory created when the container starts. Any new files created (e.g. logs) are written here.
  3. Copy-on-Write (COW): If the container modifies a shared file from the LowerDir (e.g. /etc/hosts), the kernel copies that one file up to the UpperDir and modifies it there. The shared base image remains 100% pristine!

container security: capabilities, seccomp & microvms

Because all containers share the host Linux kernel, if a container runs as root and has access to all kernel syscalls, a zero-day vulnerability in the Linux kernel allows the attacker to execute a Container Escape and compromise the entire physical server!

⚠️ defense-in-depth: the three barriers
1. Linux Capabilities: Traditional Unix divided privileges into root (UID 0) vs non-root. Linux splits root privileges into 40+ granular capabilities. Docker drops dangerous capabilities by default (e.g. CAP_SYS_ADMIN, CAP_NET_RAW, CAP_SYS_PTRACE).
2. Seccomp (Secure Computing Mode): Restricts which system calls a container can execute. Docker applies a default seccomp profile that blocks over 40 dangerous syscalls (like reboot and sys_chroot).
3. MicroVMs (AWS Firecracker / Google gVisor): How does AWS Lambda run untrusted code from 1,000 different customers on the same EC2 instance? Not using raw Docker! AWS built Firecracker: minimalist virtual machines that use KVM hardware-virtualization to provide true hypervisor-level security boundaries while booting in under 5 milliseconds with only 5MB memory overhead!

quick check

  • Does a Docker container run its own operating system kernel? No. It shares the host machine's Linux kernel.
  • Which Linux namespace provides isolated IP addresses and network routes? The NET namespace (CLONE_NEWNET).
  • What happens when a container exceeds its cgroup memory limit? The Linux kernel OOM killer terminates the container process with exit code 137.

the 20-second summary

Virtual Machines simulate complete hardware to run isolated guest kernels using hypervisors (KVM), incurring startup and memory penalties. Containers achieve near-zero-overhead isolation on a shared Linux kernel by combining Namespaces (for visibility partitioning), Cgroups (for CPU/memory throttling), and OverlayFS (for layered copy-on-write storage). In multi-tenant environments, security is hardened through Seccomp, Linux capabilities, or hardware-assisted MicroVMs like AWS Firecracker.
