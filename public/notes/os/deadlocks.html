the four-way gridlock — coffman's conditions, banker's algorithm, and dining philosophers.

the 30-second elevator pitch

Thread 1 holds Lock A and waits for Lock B. At the exact same microsecond, Thread 2 holds Lock B and waits for Lock A. Neither thread can proceed, neither thread will yield, and neither thread will ever unlock their held lock. Both threads freeze forever. This is a Deadlock.

  • The 4-Way Traffic Intersection: Four cars arrive at an unmarked four-way stop simultaneously. Car 1 yields to Car 2 on its right, Car 2 yields to Car 3, Car 3 yields to Car 4, and Car 4 yields to Car 1. Everyone waits politely forever. No single car can move without breaking the rule.
  • The Universal Rule: For a deadlock to exist, four mathematical conditions must hold simultaneously. If you break even one single condition, deadlock becomes physically impossible!
🧷 the 4 coffman conditions (1971)
A deadlock occurs if and only if all four conditions hold concurrently:
  1. Mutual Exclusion: At least one resource must be held in a non-shareable mode (only one process at a time can use it).
  2. Hold and Wait: A process must be actively holding at least one resource while waiting to acquire additional resources held by others.
  3. No Preemption: Resources cannot be forcibly snatched away from a process; they can only be released voluntarily by the holder upon task completion.
  4. Circular Wait: There exists a closed chain of processes $\{P_0, P_1, \dots, P_n\}$ such that $P_0$ waits for a resource held by $P_1$, $P_1$ waits for $P_2$, and $P_n$ waits for $P_0$.

resource allocation graphs (RAG)

The operating system models resource states as a directed graph $G = (V, E)$:

  • Nodes ($V$): Circles represent Processes ($P_i$); Rectangles represent Resources ($R_j$), with internal dots representing the number of available instances.
  • Request Edge ($P_i \to R_j$): Directed edge from process to resource indicates $P_i$ is waiting to acquire an instance of $R_j$.
  • Assignment Edge ($R_j \to P_i$): Directed edge from a specific dot in $R_j$ to $P_i$ indicates $P_i$ currently holds that instance.
⚠️ cycle does NOT always mean deadlock
If every resource has strictly ONE instance: A cycle in the Resource Allocation Graph is a necessary AND sufficient condition for deadlock (Cycle $\iff$ Deadlock).
If resources have MULTIPLE instances: A cycle is merely a necessary condition, not sufficient! If another process holds an instance of the cycled resource and finishes, it can break the cycle.

the 4 ways to handle deadlocks

1. Deadlock Prevention (design out the Coffman conditions)

Eliminate deadlocks at compile time by making one of the 4 conditions physically impossible:

  • Break Mutual Exclusion: Make all resources shareable (e.g. read-only files). Unrealistic for databases or hardware printers.
  • Break Hold and Wait: Require processes to request all needed resources at program launch. If even one is unavailable, allocate none. (Severe flaw: terrible resource utilization).
  • Break No Preemption: If Process A requests a locked resource, the OS forcibly takes away all other resources Process A currently holds and puts it to sleep.
  • Break Circular Wait (The Production Standard): Lock Ordering / Resource Hierarchy. Assign every resource an integer ID. Enforce the global rule: Threads must ALWAYS acquire locks in strictly ascending numerical order ($L_1 \to L_2 \to L_3$). Circular wait becomes mathematically impossible!

2. Deadlock Avoidance: Dijkstra's Banker's Algorithm

Before granting any resource request, the OS simulates the future. If allocating the resource keeps the system in a Safe State (a state where there exists at least one order in which all processes can finish), grant it. If the state becomes Unsafe, block the caller.

🔬 worked example: banker's algorithm trace
Consider 5 processes ($P_0$ to $P_4$) and 3 resource types ($A=10, B=5, C=7$).
Current snapshot:
Available: $A=3, B=3, C=2$
Need Matrix ($Need = Max - Allocation$):
$P_0$: $[7, 4, 3]$ | $P_1$: $[1, 2, 2]$ | $P_2$: $[6, 0, 0]$ | $P_3$: $[0, 1, 1]$ | $P_4$: $[4, 3, 1]$
  1. Can $P_0$ run? Need $[7, 4, 3] > Available [3, 3, 2]$. No.
  2. Can $P_1$ run? Need $[1, 2, 2] \le Available [3, 3, 2]$. YES! $P_1$ finishes and releases its held resources ($[2, 0, 0]$). New Available: $[3+2, 3+0, 2+0] = [5, 3, 2]$.
  3. Can $P_3$ run? Need $[0, 1, 1] \le [5, 3, 2]$. YES! Releases its $[2, 1, 1]$. New Available: $[7, 4, 3]$.
  4. Can $P_4$ run? Need $[4, 3, 1] \le [7, 4, 3]$. YES! Releases $[0, 0, 2]$. New Available: $[7, 4, 5]$.
  5. Can $P_0$ run? Need $[7, 4, 3] \le [7, 4, 5]$. YES! Releases $[0, 1, 0]$.
  6. Finally, $P_2$ finishes.
Conclusion: System is in a Safe State with safe execution sequence $\langle P_1, P_3, P_4, P_0, P_2 \rangle$.
⚠️ why general OSes don't use Banker's
The Banker's algorithm requires knowing the maximum resource demand of every process in advance. In real desktop and cloud systems, a user can arbitrarily open 500 browser tabs or allocate 10GB of memory. It is impossible to know peak demand beforehand!

3. Deadlock Detection & Recovery

Allow deadlocks to occur, run an $O(V+E)$ cycle detection algorithm on a Wait-For Graph periodically, and recover by forcibly killing processes (victim selection) or rolling back to a saved checkpoint.

4. The Ostrich Algorithm (The Industry Reality)

Stick your head in the sand and pretend deadlocks never happen. Linux, Windows, and macOS use the Ostrich Algorithm for general processes. Why? Because deadlocks are relatively rare, and continuously checking graphs or running safety matrices on every single mutex lock/unlock would degrade system throughput by 30%.

classic interview problem: the dining philosophers

Five philosophers sit around a circular table with 5 bowls of rice and 5 chopsticks. A philosopher needs two chopsticks (left and right) to eat.

⚠️ the naive strategy deadlock
Suppose every philosopher follows this intuitive rule:
  1. Reach out and grab your left chopstick.
  2. Wait until your right chopstick is free, then grab it.
  3. Eat, then put both chopsticks down.
The Disaster: If all 5 philosophers sit down simultaneously and grab their left chopstick at the exact same microsecond, each philosopher now holds 1 chopstick and waits indefinitely for the right chopstick held by their neighbor. All four Coffman conditions are satisfied — total circular deadlock!

production solutions

  1. Resource Hierarchy (Total Ordering): Philosophers 0 through 3 pick up lower-numbered chopstick first, then higher. Philosopher 4 must pick up chopstick 0 before chopstick 4! The cycle is broken.
  2. Arbitrator / Waiter: A counting semaphore initialized to 4 limits the table to at most 4 philosophers simultaneously. By Pigeonhole Principle, at least one philosopher is guaranteed both chopsticks.
  3. Asymmetric Strategy: Odd philosophers pick left then right; even philosophers pick right then left.

deadlock vs livelock vs starvation

ConditionProcess StateCPU UtilizationResolution
Deadlock Blocked / Sleeping 0% CPU burned External intervention required (kill process or reboot).
Livelock Active / Running 100% CPU burned Processes continually change state in response to each other without making progress (like two polite people trying to step aside in a hallway). Solved via randomized backoff (Ethernet CSMA/CD).
Starvation Ready / Waiting Normal A process waits indefinitely while higher-priority processes hog the resource. Solved via Aging.

quick check

  • What are the four Coffman conditions? Mutual Exclusion, Hold and Wait, No Preemption, Circular Wait.
  • How does lock ordering prevent deadlocks in production? It imposes a strict total order on lock acquisitions, mathematically preventing Circular Wait.
  • What is the difference between an unsafe state and a deadlocked state? An unsafe state is not necessarily deadlocked; it is merely a state from which the OS cannot guarantee avoiding a future deadlock.

the 20-second summary

Deadlocks occur when threads circularly hold resources while waiting for each other, requiring all four Coffman conditions to hold. While Dijkstra's Banker's Algorithm mathematically avoids deadlocks, production operating systems rely on the Ostrich algorithm, pushing responsibility to software engineers to enforce strict lock ordering (hierarchical locking) to eliminate circular waiting at the application layer.
