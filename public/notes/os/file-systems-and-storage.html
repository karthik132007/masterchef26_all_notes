from silicon sectors to directory trees — inodes, the vfs layer, ext4 journaling, and fsync.

the 30-second elevator pitch

A hard disk or SSD is simply an enormous array of billions of raw, unlabelled 512-byte or 4096-byte sectors. It has no concept of "files", "folders", or "permissions". A File System is the data structure that imposes order on this chaos, organizing raw disk blocks into human-readable directory trees and files that persist across system reboots.

  • The Library Index Card Analogy: A book is not a single continuous scroll. The pages are scattered across physical shelves. The Inode (Index Node) is the library catalog card that records who owns the book, when it was checked out, and the exact shelf numbers where every chapter is stored.
  • The Golden Separation: In Unix, a file's name is completely decoupled from the file's data! A directory is just a special file containing a table that maps human names to Inode numbers.
🧷 the three file tables
When your code opens a file, three separate tables coordinate access:
1. Per-Process File Descriptor Table: Maps integer FDs (0, 1, 2, 3...) to Open File Table entries.
2. System-Wide Open File Table: Tracks active file status, access flags (read/write), current byte offset, and reference count.
3. System-Wide Inode Table: Holds the real on-disk metadata and pointers to raw physical disk storage blocks.

deep dive: inside the unix inode

Every file and directory in a Unix filesystem is represented by an Inode. An Inode stores everything about a file except its name and its actual data content:

FieldContent
File ModeFile type (regular file, directory, symlink, socket, pipe) + Permissions (rwxr-xr-x).
OwnershipUser ID (UID) and Group ID (GID).
SizeFile size in bytes.
Timestampsatime (last accessed), mtime (last modified), ctime (inode metadata changed).
Link CountNumber of directory hard links pointing to this Inode.
Block PointersArray of physical disk block addresses (Direct, Single, Double, and Triple indirect pointers).

the multi-level indirect block pointer architecture

How does a fixed-size 128-byte Inode point to both a 10-byte text file and a 50-gigabyte database file?

  • 12 Direct Pointers: Point directly to raw data blocks on disk. For files $\le 48\text{ KB}$ ($12 \times 4\text{ KB}$), accessing data requires zero indirect hops!
  • 1 Single Indirect Pointer: Points to a disk block filled with 1,024 block pointers ($1,024 \times 4\text{ KB} = 4\text{ MB}$).
  • 1 Double Indirect Pointer: Points to a block containing pointers to 1,024 single indirect blocks ($1,024 \times 1,024 \times 4\text{ KB} = 4\text{ GB}$).
  • 1 Triple Indirect Pointer: Points to a block containing pointers to double indirect blocks ($1,024^3 \times 4\text{ KB} = 4\text{ Terabytes}$).

hard links vs soft (symbolic) links

Hard Link (ln file.txt link1)

Creates a brand-new directory entry pointing to the exact same Inode number as the original file.

  • Both filenames share the exact same permissions, timestamps, and data blocks.
  • Increments the Inode's link count by 1.
  • If you delete file.txt, the data is NOT deleted! The link count drops to 1, and link1 continues to access the data. Disk space is only reclaimed when link count hits 0 and all open file descriptors close.
  • Limitation: Cannot cross filesystem partitions.

Soft / Symbolic Link (ln -s file.txt link2)

A completely independent file with its own unique Inode, whose data content is simply a text string representing the target file's path.

  • Works like a Windows shortcut.
  • If you delete file.txt, link2 becomes a dangling symlink pointing to a non-existent path.
  • Advantage: Can link to directories and can span across different physical hard drives and filesystems.

the virtual file system (VFS): the universal abstraction

Why can your Python program use open() and read() seamlessly across an Ext4 SSD partition, a USB stick formatted in FAT32, a network drive on NFS, and pseudo-filesystems like /proc and /dev?

Because the Linux kernel sits on top of the VFS (Virtual File System) layer:

  1. Superblock Object: Represents an entire mounted filesystem (stores block size, total free blocks, filesystem magic number).
  2. Inode Object: Represents an individual file's metadata across any filesystem type.
  3. Dentry (Directory Entry) Object: Caches path-to-inode mappings (e.g. /usr/bin/python) in memory (the dcache) to eliminate repeated disk reads for path resolution.
  4. File Object: Represents an actively opened file instance for a specific process (tracks current read/write offset).

crash consistency & ext4 journaling

What happens if you are appending data to a file and the power plug is violently yanked out midway through? Appending a block requires three separate disk writes:

  1. Write the actual Data Block to disk.
  2. Update the Inode's size and block pointers.
  3. Update the Free Data Block Bitmap to mark the sector as occupied.

If power cuts after step 2 but before step 3, the Inode points to a block that the bitmap thinks is free! Another file will overwrite it tomorrow, causing silent data corruption. This is the Crash Consistency Problem.

the fix: journaling (Write-Ahead Logging for filesystems)

Before modifying the real filesystem structures, the kernel writes a log of its intended changes to a dedicated circular disk area called the Journal:

🔬 ext4's three journaling modes
- 1. Data Journaling (Safest, Slowest): Both file data and metadata are written to the journal before writing to the main filesystem. Everything is double-written to disk.
- 2. Ordered Journaling (Linux Default): File data is written to disk first. Once written, only metadata is committed to the journal. Prevents garbage data exposure without paying a double-write penalty for large files.
- 3. Writeback Journaling (Fastest, Riskiest): Metadata is journaled, but no order is enforced relative to data writes. After a crash, recently appended files may contain stale garbage sectors.

production systems: why databases demand fsync()

When your app calls write(fd, buffer, 1024), it does NOT write to the physical SSD! The kernel copies your buffer into the in-memory Page Cache in RAM and immediately returns success in 5 microseconds.

The kernel flushes dirty page-cache pages asynchronously every 30 seconds. If power fails at second 28, your data is lost!

⭐ write() vs fsync() vs fdatasync()
- write(): Buffers data in RAM Page Cache. Fast, non-durable.
- fsync(fd): Blocks the calling thread until all buffered data AND inode metadata updates are physically committed to non-volatile disk platters/SSD flash.
- fdatasync(fd): Flushes data, but skips non-essential metadata (like access timestamp), saving an entire extra disk seek!
- Database Rule: PostgreSQL, MySQL (InnoDB), and SQLite call fsync() on their Write-Ahead Log (WAL) on every transaction commit. Without fsync(), ACID durability does not exist!

quick check

  • Does an Inode store the file's name? No. The filename is stored in the directory's data block, which maps names to Inode numbers.
  • What happens to a file's physical data on disk when you delete it with rm while another process has it open? The directory entry is removed and link count drops, but the physical disk blocks and Inode remain alive until the process closes the open file descriptor.
  • Why do databases use fdatasync() instead of fsync()? To avoid flushing harmless metadata updates (like access timestamps), cutting disk write overhead in half.

the 20-second summary

The file system abstracts raw disk sectors into hierarchical files using Inodes to store metadata and multi-level block pointers to index data blocks. The Virtual File System (VFS) provides a polymorphic interface across all storage drivers. Modern filesystems like Ext4 employ journaling to survive unexpected power failures, while mission-critical databases bypass lazy page-cache buffering using fsync() to guarantee on-disk durability.
