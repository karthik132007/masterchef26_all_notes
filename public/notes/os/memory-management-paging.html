the magic of the mmu — page tables, tlb caches, address translation math, and hugepages.

the 30-second elevator pitch

Every pointer in your code (e.g. 0x7ffee4b2a190) is a complete fiction. It does not correspond to physical copper pins or memory chips on your motherboard. It is a Virtual Address.

  • The Postal P.O. Box Analogy: Your code has a virtual P.O. Box number. Behind the counter, the post office (the CPU's Memory Management Unit - MMU) consults a private ledger (the Page Table) and translates that P.O. Box to a physical street address in real RAM.
  • Why do this?
    1. Total Memory Protection: Process A cannot touch Process B's memory because their page tables map to completely different physical silicon frames.
    2. No Contiguous Requirement: Your app can request a contiguous 1GB array, but the OS can scatter it across 250,000 fragmented, non-adjacent 4KB blocks in RAM without your app ever knowing!
🧷 core vocabulary
Virtual Page: A fixed-size block of virtual memory (standard: 4 KB).
Physical Frame (Page Frame): A matching fixed-size block of physical RAM (4 KB).
MMU (Memory Management Unit): The hardware chip inside the CPU that performs wire-speed address translation.

fragmentation: internal vs external

Fragmentation TypeWhere It OccursDefinitionFix
External Fragmentation Contiguous Allocation & Segmentation Total free memory space exists to satisfy a request, but it is broken into tiny, non-contiguous holes too small to fit the process. Paging completely eliminates external fragmentation by allowing allocations to be non-contiguous.
Internal Fragmentation Paging Allocated memory is slightly larger than requested memory. Unused space inside the final allocated page. Unavoidable in fixed-block architectures, but average loss is only $\frac{\text{Page Size}}{2} = 2\text{ KB}$ per allocation.

address translation: step-by-step math

A virtual address is partitioned into two bitfields: Page Number ($p$) and Page Offset ($d$).

Virtual Address = [ Page Number (p) | Offset (d) ]
Page Size = $2^m$ bytes $\implies$ Offset requires $m$ bits.
Address Space = $2^n$ bytes $\implies$ Address has $n$ total bits; Page Number has $(n - m)$ bits.
🔬 worked example: translating an address
Consider a 32-bit architecture with a 4 KB page size ($4\text{ KB} = 4096\text{ bytes} = 2^{12}\text{ bytes}$).
- Offset $d$ = 12 bits.
- Page Number $p$ = $32 - 12 = 20$ bits.
Translate virtual hex address 0x00003A4C:
1. Separate page number and offset: Page Number $p = \text{0x00003}$, Offset $d = \text{0xA4C}$.
2. Consult Page Table at index 3. Suppose the Page Table Entry says: Frame Number = 7 (0x00007).
3. Physical Address = $[\text{Frame Number} \mid \text{Offset}] = \text{0x00007A4C}$!

multi-level paging: why flat page tables are impossible

Why can't the OS just keep a single simple array for all page translations? Let's do the math on a modern 64-bit system:

  • Page size = 4 KB ($2^{12}$).
  • Virtual address space = $2^{64}$ bytes. Number of pages = $\frac{2^{64}}{2^{12}} = 2^{52}$ pages.
  • If each Page Table Entry (PTE) takes 8 bytes, a single flat table would require: $$2^{52} \times 8\text{ bytes} = 2^{55}\text{ bytes} \approx \mathbf{33\text{ Petabytes of RAM!}}$$
  • Your machine would run out of memory before creating a page table for even one process!

the solution: 4-level page tables (x86-64 PML4)

Modern 64-bit CPUs use 48-bit canonical virtual addresses broken into four 9-bit chunks plus a 12-bit offset:

48-bit Address: [ PML4: 9 bits | PDPT: 9 bits | PD: 9 bits | PT: 9 bits | Offset: 12 bits ]
$9 + 9 + 9 + 9 + 12 = 48\text{ bits}$ (Provides 256 Terabytes of virtual memory).

Why does this save memory? The page table is a sparse tree! If an app only allocates 2MB on the heap, the OS only creates the few tree branches corresponding to that address. Unallocated gigabytes consume zero bytes of page table memory!

the translation lookaside buffer (TLB)

Multi-level paging solved the storage crisis, but introduced a catastrophic latency crisis: To read a single 4-byte integer from RAM, the CPU has to walk 4 levels of page tables in RAM first!

$$\text{Memory Access} = 4\text{ page table reads} + 1\text{ data read} = \mathbf{5\text{ RAM lookups}}\ (5 \times 100\text{ns} = 500\text{ns})!$$

The silicon fix is the TLB (Translation Lookaside Buffer): an ultra-fast, on-chip associative hardware SRAM cache inside the MMU that caches the last few thousand virtual-page-to-physical-frame translations in ~0.5 nanoseconds.

🔬 formula: effective memory access time (EMAT)
Let $\alpha$ be the TLB Hit Ratio, $T_{\text{tlb}}$ be TLB lookup time (1ns), and $T_{\text{ram}}$ be RAM access time (100ns).
On a 4-level page table system:
$$\text{EMAT} = \alpha \times (T_{\text{tlb}} + T_{\text{ram}}) + (1 - \alpha) \times (T_{\text{tlb}} + 4 \times T_{\text{ram}} + T_{\text{ram}})$$ If TLB Hit Ratio $\alpha = 98\%$:
$$\text{EMAT} = 0.98 \times (1 + 100) + 0.02 \times (1 + 500) = 98.98 + 10.02 = \mathbf{109\text{ ns}}$$ A 98% hit ratio keeps memory speeds close to native hardware speed!

faang performance deep-dive: hugepages

At Google and Meta, large memory-intensive applications (Redis, PostgreSQL, Java heaps, PyTorch tensor training) can spend 20% to 30% of their total CPU cycles solely stalled on TLB misses!

  • The Problem: Standard pages are 4 KB. If Redis holds 32 GB of data in memory, that requires $\frac{32\text{ GB}}{4\text{ KB}} = \mathbf{8,388,608\text{ page entries}}$. But a CPU's L1/L2 TLB only holds ~1,500 entries! The TLB constantly thrashes.
  • The Solution: HugePages (2 MB and 1 GB):
    • x86-64 CPUs allow skipping the bottom page table level: mapping a 2 MB page directly at the Page Directory level (21-bit offset).
    • Covering 32 GB with 2 MB HugePages requires only $\frac{32\text{ GB}}{2\text{ MB}} = \mathbf{16,384\text{ entries}}$ (a 512x reduction!).
    • TLB coverage increases by 512x, slashing TLB misses from 25% to under 1% and delivering double-digit throughput leaps!
⚠️ gotcha: tlb shootdown latency
When a thread on Core 1 unmaps or modifies a page table entry, the other 63 CPU cores might still hold the stale translation in their local TLBs. Core 1 must send an Inter-Processor Interrupt (IPI) across the motherboard to all 63 cores forcing them to flush their TLBs. This is called a TLB Shootdown—a major scalability bottleneck in high-core cloud servers.

quick check

  • Does paging suffer from external fragmentation? No, because physical frames do not need to be contiguous.
  • What hardware register points to the root of the active page table tree? The CR3 register on x86.
  • How many levels of page tables are used in standard 48-bit x86-64 virtual addressing? 4 levels (PML4, PDPT, PD, PT).

the 20-second summary

The MMU translates virtual addresses to physical frames using page tables, guaranteeing process isolation and eliminating external fragmentation. Because flat page tables for 64-bit spaces would require tens of petabytes of RAM, modern OSes use sparse multi-level page tables cached by the hardware TLB. High-performance production systems deploy 2MB HugePages to prevent TLB thrashing when managing tens of gigabytes of RAM.
