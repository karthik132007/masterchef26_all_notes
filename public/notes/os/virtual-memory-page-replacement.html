the art of living beyond your physical ram — page faults, belady's anomaly, and the linux oom killer.

the 30-second elevator pitch

Your server has 16 GB of physical RAM, but you are running a database using 12 GB, 5 microservices using 8 GB, and an ML model using 6 GB (total = 26 GB). How does your computer not explode? Through Virtual Memory & Demand Paging.

  • The Desk vs The Bookshelf Analogy: Your physical desk (RAM) only has room for 3 open textbooks. The library bookshelf (SSD / Swap space) holds 1,000 textbooks. You don't bring all 1,000 books to your desk at once. You keep the 3 books you are actively studying right now on the desk. When you need a 4th book, you move one idle book back to the shelf to make room.
  • Demand Paging: Never load a page of memory from disk into RAM until the CPU actively attempts to execute or read from it ("lazy loading at the hardware level").
🧷 the valid / invalid bit
Every Page Table Entry (PTE) contains a hardware Present/Valid Bit:
- Bit = 1: The page is resident in physical RAM. MMU translates address instantly.
- Bit = 0: The page is either unmapped (illegal access) or swapped out on disk. Accessing it triggers a Page Fault Exception.

the 6-step lifecycle of a page fault

What physically occurs inside the CPU and kernel when your code touches a non-resident page?

1
Hardware Trap: CPU attempts to read address. MMU sees Valid Bit = 0 and raises a hardware Page Fault Exception (Interrupt 14 on x86).
2
Kernel Validity Check: The OS kernel takes over in Ring 0 and consults the process's Virtual Memory Areas (VMAs). If the address is outside valid allocations, the kernel fires SIGSEGV (Segmentation Fault). If valid, it proceeds.
3
Frame Allocation: The kernel searches for a free physical RAM frame. If RAM is completely full, it runs a Page Replacement Algorithm to evict an existing victim page to disk.
4
Disk I/O Transfer: The OS issues a DMA read request to load the 4KB page from the swap space / SSD file into the allocated physical frame. The faulting thread is put to sleep (WAITING).
5
Update Page Table: The disk controller fires a hardware interrupt signaling the transfer is complete. The kernel writes the physical frame number into the PTE and sets Valid Bit = 1.
6
Instruction Restart: The kernel returns from interrupt. The CPU hardware restarts the exact assembly instruction that caused the fault! This time, the MMU finds Valid Bit = 1 and succeeds transparently.

page replacement algorithms

1. Optimal Page Replacement (Belady's Min Algorithm)

Replace the page that will not be used for the longest period of time in the future. Provably produces the lowest possible number of page faults. However, it is an impossible algorithm in real OSes because the kernel cannot see the future! It is used solely as a theoretical benchmark.

2. FIFO & Belady's anomaly

Evict the oldest page loaded in memory using a simple queue. Intuition suggests that giving a process more physical memory frames will always reduce page faults. With FIFO, this intuition is dead wrong!

⚠️ belady's anomaly proof
Consider the page reference string: 1, 2, 3, 4, 1, 2, 5, 1, 2, 3, 4, 5
- With 3 physical frames: Tracing FIFO yields 9 Page Faults.
- With 4 physical frames: Tracing FIFO yields 10 Page Faults!
Adding more memory caused more page faults! FIFO suffers from Belady's Anomaly because it does not belong to the class of Stack Algorithms (algorithms where the set of pages in memory for $N$ frames is always a strict subset of pages for $N+1$ frames).

3. Least Recently Used (LRU)

Evict the page that has not been accessed for the longest period of time. Approximates the optimal algorithm by using the recent past to predict the future (Temporal Locality). Never suffers from Belady's Anomaly.

Why doesn't Linux implement pure LRU? Pure LRU requires updating a doubly-linked list or timestamp register on every single memory access! Doing that on billions of CPU read/writes per second would incinerate memory performance.

4. The Clock Algorithm (Second-Chance Algorithm)

How real operating systems approximate LRU with almost zero hardware overhead:

  1. The CPU hardware sets a 1-bit Reference Bit in the PTE to 1 whenever a page is read or written.
  2. The OS organizes all physical frames into a circular queue with a pointer (the Clock Hand).
  3. When a page must be evicted:
    • If the frame under the hand has $\text{Reference Bit} = 1$: The OS clears it to $0$ ("gives it a second chance") and advances the hand to the next frame.
    • If the frame has $\text{Reference Bit} = 0$: This page is evicted! The new page takes its place, and the hand advances.

thrashing & the working set model

If a process does not have enough physical frames to hold its actively used pages, it spends 99% of its time waiting for pages to be swapped in and out of disk. CPU utilization collapses to near 0%. This state is called Thrashing.

the working set model (Peter Denning)

  • Working Set Window ($\Delta$): A fixed number of recent page references (e.g. last 10,000 references).
  • Working Set ($WSS_i$): The total number of distinct pages process $P_i$ accessed inside window $\Delta$.
  • The Anti-Thrashing Condition: Total memory demand $D = \sum WSS_i$.
    • If $D \le \text{Total Physical RAM}$: The system runs smoothly.
    • If $D > \text{Total Physical RAM}$: Thrashing begins. The OS scheduler must suspend (swap out) an entire process to free its frames for others.

production linux internals: kswapd & the oom killer

In production Linux servers, memory reclamation operates in two tiers:

  1. Background Reclamation (kswapd daemon): When free RAM drops below the low watermark, the kernel wakes up kswapd asynchronously to write dirty pages to disk and reclaim clean page-cache frames. Applications continue running without pause.
  2. The OOM (Out Of Memory) Killer: When free RAM drops to zero and direct reclamation fails, the kernel must kill a process to prevent a complete hardware kernel panic.
⭐ how linux chooses which process to kill (oom score)
The kernel calculates a score from 0 to 1000 for each process: $$\text{badness\_score} \approx \frac{\text{RSS Memory Used}}{\text{Total RAM}} \times 1000 + \text{oom\_score\_adj}$$ - The process consuming the most RAM with the lowest priority gets killed first with SIGKILL.
- Production Tip: Critical processes (like an SSH daemon or Redis database) can be granted immunity by writing -1000 into /proc/<PID>/oom_score_adj. A value of -1000 removes the process from OOM consideration entirely!

quick check

  • What triggers a Page Fault? An attempt to access a virtual page whose PTE has Valid Bit = 0.
  • Which page replacement algorithm suffers from Belady's Anomaly? First-In, First-Out (FIFO).
  • What is the difference between pure LRU and the Clock Algorithm? Pure LRU tracks exact access history; Clock uses a single hardware-set Reference bit per page to give pages a second chance.

the 20-second summary

Virtual memory allows systems to exceed physical RAM capacity by demand-paging 4KB blocks between disk and memory. When an unmapped page is referenced, the CPU triggers a Page Fault, prompting the kernel to allocate a frame, read from disk, update page tables, and restart the instruction. If physical memory becomes oversubscribed, the system risks thrashing, requiring page replacement (Clock algorithm) or intervention from the Linux Out-Of-Memory (OOM) killer.
