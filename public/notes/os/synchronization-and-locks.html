preventing chaos in shared memory — race conditions, semaphores, futexes, and lock-free internals.

the 30-second elevator pitch

Imagine a shared whiteboard where two people simultaneously try to update a bank balance: balance = balance + 10. Person A reads $100. Before Person A writes $110, Person B also reads $100. Both write $110. Ten dollars has vanished into thin air! This is a Race Condition.

  • The Critical Section: Any piece of code that accesses shared mutable state (a global counter, a linked list, a database socket). Only one thread may execute inside this section at any instant.
  • The Airplane Bathroom Analogy: A mutex is the lock on the airplane bathroom door. If it is green (unlocked), you walk in and slide it red (locked). If someone else arrives while it is red, they must wait outside until you unlock it.
🧷 the 3 critical section rules
Any valid synchronization solution must satisfy three properties:
  1. Mutual Exclusion: If Thread A is executing in its critical section, no other thread can be executing in that section.
  2. Progress: If no thread is in the critical section and someone wants to enter, only threads actively competing may participate in the decision, and the selection cannot be postponed indefinitely.
  3. Bounded Waiting: There must be a limit on the number of times other threads can enter before a waiting thread's request is granted (no infinite starvation).

hardware primitives: test-and-set & compare-and-swap (CAS)

Software algorithms alone (like Peterson's algorithm) break on modern out-of-order CPUs because hardware reorders instructions and caches memory. Hardware must provide atomic instructions (uninterruptible at the silicon memory-bus level):

compare-and-swap (CAS / x86 CMPXCHG)

The foundation of all modern concurrent lock-free data structures. The CPU silicon implements this in a single indivisible memory bus transaction:

  • Input: A target memory address, an expected old value, and a desired new value.
  • Operation: The hardware inspects the memory address. If the current value matches the expected value, it writes the new value and reports success. If another core intervened and changed the value, it aborts without modifying memory and reports failure.
  • Atomicity: Guaranteed by hardware bus locking or cache-line locking protocols (e.g., MESI).

spinlocks vs mutexes: when to spin vs when to sleep?

Spinlock (Busy Waiting)

The thread sits in an active CPU loop continuously probing the lock flag via atomic instructions until it becomes free.

  • Pros: Zero context switch overhead. Responds instantly the moment the lock is released.
  • Cons: Burns 100% CPU power doing zero useful work while waiting. Horrible on single-core machines.
  • Use Case: Operating system kernel interrupt handlers where threads cannot sleep, or critical sections holding a lock for $< 50\text{ns}$.

Mutex (Sleeping Lock)

If the lock is busy, the thread yields the CPU. The OS moves the thread from RUNNING to WAITING and schedules another task.

  • Pros: Frees the CPU core for other useful processes to execute. Zero power wasted spinning.
  • Cons: High overhead: going to sleep and waking up requires two context switches (~2–4 microseconds).
  • Use Case: General application code where critical sections hold locks for milliseconds (disk, network, complex calculations).
⚠️ the golden decision rule
If (Estimated Lock Hold Time < 2 $\times$ Context Switch Latency): Use a Spinlock.
If (Estimated Lock Hold Time > 2 $\times$ Context Switch Latency): Use a Mutex.
Modern adaptive mutexes (like in Linux pthreads and Java HotSpot) do both: they spin for 100 iterations; if still locked, they put the thread to sleep!

semaphores: counting vs binary

Invented by Edsger Dijkstra in 1965. An integer variable S modified only by two atomic operations: wait() (originally P for proberen, to test) and signal() (originally V for verhogen, to increment).

  • Binary Semaphore: Value is 0 or 1. Functions similarly to a mutex, with one crucial difference: A semaphore has no ownership concept! Thread A can lock it, and Thread B can unlock it (useful for signaling between threads). A Mutex must be unlocked by the exact same thread that acquired it.
  • Counting Semaphore: Initialized to an integer $N$ (e.g., $N=10$). Controls access to a finite pool of $N$ identical resources (e.g., database connection pool of 10 connections). Every wait() decrements; when count hits 0, subsequent callers block until another thread calls signal().

classic problem: producer-consumer (bounded buffer)

How do producers and consumers share a finite buffer of $N$ slots without race conditions or buffer overflow?

SemaphoreInitial ValueRole in Coordination
mutex1Guarantees mutual exclusion: only one thread modifies the buffer queue at any instant.
empty_slots$N$Tracks empty slots. Producer decrements (blocks when 0); consumer increments after consuming.
full_slots0Tracks populated slots. Consumer decrements (blocks when 0); producer increments after producing.
  • Producer Flow: Check empty_slots (sleep if buffer full) $\to$ Acquire mutex $\to$ Insert item into buffer $\to$ Release mutex $\to$ Signal full_slots (wakes up sleeping consumer).
  • Consumer Flow: Check full_slots (sleep if buffer empty) $\to$ Acquire mutex $\to$ Remove item from buffer $\to$ Release mutex $\to$ Signal empty_slots (wakes up sleeping producer).

condition variables & spurious wakeups

A Condition Variable (CV) allows threads to sleep until a specific application condition is satisfied. It always works in conjunction with an associated mutex.

⚠️ why a while loop is mandatory (spurious wakeups)
In every systems interview, you will be asked why a condition variable wait must always sit inside a while loop, never an if statement:
  • The Broken Approach (if check): Testing the condition once before waiting. If the thread wakes up, it blindly assumes the condition is met and proceeds immediately.
  • The Safe Approach (while check): Testing the condition in a loop. When awakened, the thread loops back to re-verify the condition before executing further.
Why this is mandatory:
  1. Spurious Wakeups: The OS kernel or POSIX implementation can occasionally wake up a sleeping thread even when no signal was issued!
  2. The Thundering Herd Race: When a thread signals or broadcasts, multiple waiting threads wake up. Thread 1 acquires the mutex first and consumes the item. When Thread 2 gets the mutex next, the condition is no longer true! A while loop safely catches this and puts Thread 2 back to sleep.

under the hood: how linux futex (fast userspace mutex) works

Before Linux 2.6, acquiring a mutex meant issuing a sys_semop system call every single time—costing 100ns per lock even when zero other threads were competing for it! Linux revolutionized this with futex (Fast Userspace Mutex):

  1. The Fast Path (Uncontended): When Thread 1 locks an uncontended mutex, it executes an atomic CAS instruction entirely in Ring 3 User Space. It marks the integer as locked in 5 nanoseconds with zero system calls!
  2. The Slow Path (Contended): If Thread 2 tries to acquire the lock and the CAS fails (another thread holds it), Thread 2 executes the sys_futex(val_addr, FUTEX_WAIT, ...) syscall. The kernel registers Thread 2 on an internal hash-bucket wait-queue and puts it to sleep.
  3. The Unlock: When Thread 1 finishes, it checks if any waiters exist. If none, a simple atomic user-space write unlocks it. If waiters exist, it invokes sys_futex(..., FUTEX_WAKE) to wake the sleeper.

lock-free programming & the aba problem

In high-frequency trading and low-latency queuing (like the LMAX Disruptor), locks are banned because sleeping or priority inversion destroys millisecond latency. Instead, developers use Lock-Free Algorithms backed by CAS.

⭐ the aba problem
Suppose a lock-free stack contains nodes [Top: A] → B → C.
1. Thread 1 reads Top = A and Next = B, preparing to pop A via CAS(&Top, A, B). Thread 1 is preempted.
2. Thread 2 runs, pops A, pops B, and frees both. Then it allocates a new node that happens to get the exact same memory address A and pushes it: [Top: A] → C.
3. Thread 1 wakes up and runs CAS(&Top, A, B). It sees Top == A! The CAS succeeds, setting Top = B. But B was freed! The stack now points to dangling garbage memory, corrupting the process.
The Fix: Tagged Pointers (Double-word CAS). Each pointer carries a 64-bit version counter: (Pointer, Version). When Thread 2 modifies the stack, the counter increments to $V+2$, causing Thread 1's CAS on $(A, V_1)$ to fail safely!

quick check

  • What are the three criteria required to solve the critical section problem? Mutual Exclusion, Progress, and Bounded Waiting.
  • Why does a condition variable wait call require a mutex as a parameter? Because it must atomically release the mutex and put the calling thread to sleep on the wait queue in a single indivisible step.
  • What is the difference between a mutex and a binary semaphore? A mutex has ownership (only the thread that locked it may unlock it). A semaphore can be signaled by any thread.

the 20-second summary

Concurrent threads sharing memory require synchronization to prevent race conditions. Hardware provides atomic operations like Compare-And-Swap (CAS) to build spinlocks (for microsecond pauses) and mutexes (for sleeping). Linux uses futex to achieve nanosecond locking in user space for uncontended locks, falling back to kernel wait queues only when threads collide. Always wrap condition variable waits in a while loop to defend against spurious wakeups.
