who gets the cpu next — from convoy effects and round-robin quantums to linux cfs and the mars pathfinder bug.

the 30-second elevator pitch

You have 8 CPU cores, but 250 active processes (Chrome tabs, Spotify, your IDE, background daemons). How does the operating system decide which process gets a CPU core at any millisecond, for how long, and when to kick it off? That is the job of the CPU Scheduler.

  • The Supermarket Analogy: Imagine a grocery store with one cashier (CPU). If someone with 5 cartloads gets in line first, and 10 people holding a single bottle of water wait behind them for 45 minutes, that's the Convoy Effect. A smart cashier lets quick shoppers tap out first, or serves each person 3 items before moving to the next.
  • Preemptive vs Non-Preemptive:
    • Non-Preemptive: Once a process gets the CPU, it holds it until it either terminates or yields voluntarily for I/O. (Dangerous: an infinite loop freezes the system).
    • Preemptive: The OS hardware timer interrupts the process and forcibly takes the CPU away when its allocated time slice expires. Modern general OSes are 100% preemptive.
🧷 remember: core metrics
Turnaround Time = Completion Time $-$ Arrival Time (Total time from submit to finish)
Waiting Time = Turnaround Time $-$ Burst Time (Time spent waiting in the ready queue)
Response Time = First Execution Time $-$ Arrival Time (Crucial for interactive apps!)

classical scheduling algorithms & worked traces

1. First-Come, First-Served (FCFS) & the convoy effect

Simplest algorithm: processes are executed in strict order of arrival via a standard FIFO queue. Non-preemptive.

🔬 trace: the convoy effect
Three processes arrive at time $t=0$: $P_1$ (burst = 24ms), $P_2$ (burst = 3ms), $P_3$ (burst = 3ms).
P1 (24ms)0 to 24
P2 (3ms)24 to 27
P3 (3ms)27 to 30
  • Waiting Times: $P_1 = 0$, $P_2 = 24$, $P_3 = 27$.
  • Average Waiting Time: $\frac{0 + 24 + 27}{3} = \mathbf{17\text{ ms}}$.
  • If they arrived in reverse order ($P_2, P_3, P_1$): Avg Wait = $\frac{0 + 3 + 6}{3} = \mathbf{3\text{ ms}}$! (A 5.6x improvement).

2. Shortest Job First (SJF) & Shortest Remaining Time First (SRTF)

Executes the process with the shortest CPU burst time first. Provably optimal for minimizing average waiting time.

  • Non-preemptive: SJF.
  • Preemptive: SRTF (if a new process arrives with a shorter remaining burst than the currently running process, the CPU preempts the current process).
  • The Fatal Flaw: Starvation. A continuous stream of short tasks will permanently starve long tasks. Furthermore, the OS cannot predict the exact future CPU burst duration of a user program! (Approximated using exponential smoothing: $\tau_{n+1} = \alpha t_n + (1-\alpha)\tau_n$).

3. Round Robin (RR) & time quantum sizing

Each process is allocated a small slice of CPU time called a Time Quantum ($q$), typically 10ms to 50ms. If the process is still running when $q$ expires, it is preempted and pushed to the back of the ready queue.

⚠️ gotcha: quantum trade-offs
If quantum $q \to \infty$: Round Robin degenerates into First-Come First-Served.
If quantum $q \to 0$: CPU spends 90% of its clock cycles executing context switches instead of useful code (thrashing).
Production Rule: The time quantum should be large relative to context switch overhead (~1–2µs), such that ~80% of CPU bursts are shorter than $q$.

4. Multilevel Feedback Queue (MLFQ)

The foundation of modern general-purpose schedulers. It does not require knowing burst times in advance; it learns process behavior on the fly:

  1. Processes start in the highest-priority queue with a short time quantum.
  2. If a process uses its entire time slice without yielding (CPU-bound job), it is demoted to a lower-priority queue with a longer quantum.
  3. If a process yields voluntarily for I/O before its quantum expires (interactive I/O-bound job like a text editor), it stays in the high-priority queue.
  4. Priority Boost: To prevent starvation, all processes are periodically boosted back to the top queue (e.g. every 1 second).

modern real-world: the linux completely fair scheduler (CFS)

Since Linux 2.6.23 (and enhanced through modern kernels), the default scheduling class for regular tasks is CFS (Completely Fair Scheduler). CFS discards traditional fixed time slices entirely and treats the CPU as an "ideal multi-tasking computer" where every process makes equal progress.

virtual runtime (vruntime) & the red-black tree

  • Every task in Linux tracks a 64-bit integer called vruntime (virtual runtime). It measures the amount of CPU time the process has consumed, normalized by its priority (nice value).
  • All ready tasks are ordered by their vruntime in a self-balancing Red-Black Tree.
  • Scheduling Decision: CFS always picks the leftmost node of the tree (the task that has had the least CPU time, i.e., lowest vruntime) and runs it!
  • As the task executes, its vruntime increases. When it exceeds other tasks, it is re-inserted into the tree, and the new leftmost task takes over. Finding the leftmost task is $O(1)$ (cached pointer), and tree re-insertion is $O(\log N)$.

nice values & geometric weighting

Linux nice values range from -20 (highest priority) to +19 (lowest priority), with 0 being normal.

Each nice level represents roughly a 10% difference in CPU proportion, mapped via an internal kernel weight array:

$$\Delta \text{vruntime} = \Delta \text{exec\_time} \times \frac{\text{NICE\_0\_LOAD}}{\text{task\_weight}}$$
  • If a task has nice 0, $\text{task\_weight} = 1024 = \text{NICE\_0\_LOAD}$. Its vruntime ticks up in exact real-time.
  • If a task has nice -5 (high priority), its weight is large, so its vruntime ticks up very slowly. It gets to stay on the CPU much longer before being re-sorted!
  • If a task has nice +10 (low priority / background job), its weight is small, so its vruntime shoots up rapidly, causing it to yield quickly.
⭐ exam tip: min_vruntime protection
"If a process sleeps for 3 weeks waiting on network I/O, its vruntime will be tiny compared to active processes. When it wakes up, won't it monopolize the CPU for the next 3 weeks?"
Answer: NO! Linux CFS tracks a system-wide min_vruntime. When a sleeping process wakes up, its vruntime is reset to min_vruntime - latency_target, giving it just enough boost to handle its immediate I/O packet without starving everyone else.

real-time scheduling & the mars pathfinder priority inversion bug

In July 1997, NASA's Mars Pathfinder spacecraft landed on Mars. A few days into the mission, the rover began spontaneously rebooting in the middle of data transmissions, threatening the entire mission.

  1. The Setup: A Low-priority meteorological task acquired a shared mutex lock on the information bus.
  2. The Preemption: An interrupt caused a Medium-priority communications task (which didn't need the lock) to wake up and preempt the Low-priority task.
  3. The Inversion: The High-priority attitude control task woke up and needed the information bus lock. It blocked, waiting for Low to finish. But Low couldn't finish because Medium was hogging the CPU! Medium was indirectly starving High. A watchdog timer detected the frozen High task and reset the computer.
  4. The Fix: Priority Inheritance Protocol. When a High-priority task blocks on a lock held by a Low-priority task, the Low-priority task temporarily inherits the High priority until it releases the lock, preventing any Medium-priority tasks from preempting it!

quick check

  • Why does Round Robin scheduling favor I/O bound tasks over CPU bound tasks? I/O tasks consume only a tiny fraction of their quantum before yielding, quickly jumping to the front of response queues.
  • What data structure does Linux CFS use to store ready tasks? A Red-Black Tree, ordered by vruntime.
  • How does Priority Inheritance resolve priority inversion? It elevates the priority of the lock holder to match the highest-priority blocked waiter until the lock is released.

the 20-second summary

CPU scheduling governs how cores are shared across processes. While classical algorithms like SJF are theoretically optimal, they suffer from starvation and unmeasurable burst times. Linux solves real-world fairness using the Completely Fair Scheduler (CFS), indexing tasks by their virtual runtime (vruntime) in a Red-Black tree. Real-time systems require strict preemption safety mechanisms like Priority Inheritance to prevent catastrophic priority inversion.
