from dead bytes on an ssd to a living, breathing instance on the cpu.

the 30-second elevator pitch

A program is a dead file on your hard disk (a recipe). A process is that program in active execution inside main memory (a chef actively baking the cake). When you launch five separate terminal windows running Python, you have one program on disk, but five independent processes, each with its own isolated memory space, registers, and open files.

  • The Process Abstraction: The OS gives every single process the grand illusion that it owns the entire CPU all to itself and has access to a contiguous, private memory space from address 0x0000000000000000 to 0x7FFFFFFFFFFFFFFF.
  • Total Isolation: Process A cannot read, write, or corrupt Process B's memory. If Process A crashes with a segmentation fault, Process B doesn't even flinch.
🧷 remember
A program is passive (bytes stored in an ELF binary). A process is dynamic (has a Program Counter, Stack Pointer, memory allocations, CPU registers, and state).

the virtual memory layout of a process

Every standard Linux 64-bit process is loaded into an identical virtual address layout. The address space is divided into standardized segments:

Stack (Call frames, local vars) $\downarrow$ Grows Down
$\dots$ Unallocated Guard Space $\dots$
Memory-Mapped Region (Shared libs, mmap) Shared/Dynamic
$\dots$ Unallocated Guard Space $\dots$
Heap (malloc / new dynamic memory) $\uparrow$ Grows Up
BSS Segment (Uninitialized globals/statics) Zeroed out
Data Segment (Initialized globals: int x = 42) Read/Write
Text / Code Segment (Machine instructions) Read-Only
  • Text Segment: Contains compiled machine opcodes. Marked Read-Only in the hardware MMU so a process cannot accidentally overwrite its own code. Multiple running instances of the same program (e.g. 10 bash shells) share the exact same physical RAM frames for their text segment!
  • Data Segment: Global and static variables explicitly initialized by the programmer (e.g. int max_retries = 5;).
  • BSS Segment ("Block Started by Symbol"): Global and static variables uninitialized or set to zero (e.g. int counter;). Does not take up space in the binary file on disk; the kernel zero-fills it when the process starts.
  • Heap: Dynamically allocated memory requested at runtime via malloc(), calloc(), or C++ new. Managed via the brk / sbrk syscalls or mmap. Grows upwards toward higher memory addresses.
  • Stack: Stores function activation frames, return addresses, parameters, and local variables. Managed automatically by the CPU via the Stack Pointer register (%rsp). Grows downwards toward lower addresses.

the process control block (PCB / task_struct)

To pause a process and resume it hours later without losing a single beat, the kernel needs an identity card storing its complete state. In Linux, this is the massive C struct called struct task_struct (defined in <linux/sched.h>):

the process lifecycle: 5-state and 7-state models

A process moves through distinct states during its existence:

  1. New: The process is being created and loaded into memory from an ELF binary.
  2. Ready: The process is in RAM, fully prepared to execute, waiting in the run queue for an available CPU core.
  3. Running: The process's instructions are actively being executed by a physical CPU core.
  4. Waiting (Blocked): The process requested I/O (e.g. disk read or socket packet) or is waiting on a lock/timer. It cannot use the CPU even if 100 cores were idle!
  5. Terminated: Execution finished; resources are freed, but its exit status remains until reaped by its parent.

context switching: what actually happens on the cpu

A Context Switch is the mechanism by which the CPU stops executing Process A and begins executing Process B. Here is the exact physical sequence:

  1. Trigger: Hardware timer interrupt fires (time slice expired) or Process A makes a blocking syscall (e.g. read()).
  2. Mode Switch: CPU switches to Ring 0. Hardware pushes current user registers (RIP, RSP, RFLAGS) onto Process A's kernel stack.
  3. Scheduler Invocation: The kernel scheduler algorithm selects the next task to run (Process B).
  4. Memory Context Switch: The kernel reloads the hardware CR3 register with the physical address of Process B's page directory. This completely changes the virtual-to-physical memory map!
  5. Kernel Stack Switch: The kernel changes the CPU's stack pointer to Process B's kernel stack.
  6. Restore & Return: Process B's saved CPU registers are popped off its stack. The CPU executes iretq / sysret, switching back to Ring 3. Process B resumes execution exactly where it stopped.
⚠️ gotcha
The Invisible Cost of a Context Switch: The direct CPU register swap takes ~1 to 2 microseconds. But the indirect cache pollution cost can be tens of microseconds! Changing CR3 invalidates non-global TLB entries, and Process B's memory accesses cause massive L1/L2 CPU cache misses until the cache is "warmed up."

process creation: fork(), execve(), and copy-on-write (COW)

In Unix-like systems, all processes (except PID 1 systemd) are created via the fork() and execve() system calls.

  • fork(): Creates an exact clone of the caller. Returns 0 to the child process and the child's new PID to the parent process.
  • execve(): Overwrites the current process's memory space with a completely brand-new program executable (clearing stack, heap, and code) while keeping the same PID and open file descriptors.

how copy-on-write (COW) prevents system collapse

If Redis is holding 64 GB of memory and forks a child process to write a snapshot to disk, does fork() allocate another 64 GB of physical RAM? No! If it did, your server would instantly crash with Out Of Memory.

Linux utilizes Copy-On-Write (COW):

  1. When fork() runs, the kernel does not copy physical RAM frames. It only duplicates the parent's page tables.
  2. Both parent and child page tables point to the exact same physical memory frames.
  3. The kernel marks all shared physical frames as Read-Only in the MMU page table entries.
  4. If either process merely reads memory, zero copying occurs.
  5. The instant either process attempts to write to an address, the CPU hardware raises a Page Fault exception. The kernel intercepts the fault, allocates a single new 4KB physical frame, copies just that one 4KB page, marks it Read-Write, updates the page table, and resumes execution!
🔬 the fork-exec workflow
How Unix launches new programs without code ambiguity:
  1. Step 1 (fork): The parent process invokes fork(). The OS clones the process table entry. In the parent, the call returns the child's new PID; in the child, it returns 0. Both processes branch based on this value.
  2. Step 2 (execve): The child detects it is the child (return value = 0) and calls execve() to overwrite its address space with the target executable.
  3. Step 3 (wait): The parent calls wait() to block until the child finishes, reading its exit code and cleaning up its PCB entry.

zombies vs orphan processes

TypeDefinitionProblemSolution
Zombie Process (defunct) A process that has called exit() and terminated, but whose parent has not yet read its exit status via wait() / waitpid(). Consumes no CPU or RAM, but occupies a slot in the kernel's finite PID table. If a buggy parent leaks 32,768 zombies, the OS cannot spawn any new processes! Kill the parent process, or write the parent to handle SIGCHLD and invoke waitpid().
Orphan Process A running process whose parent died or terminated before it did. Harmless. The child has no parent to report its final exit code to. The OS kernel automatically reparents the orphan to PID 1 (init or systemd). PID 1 runs a continuous loop calling wait() to reap all orphans upon termination.
⭐ exam tip
"Can you kill a Zombie process with `kill -9 <PID>`?"
Answer: NO! You cannot kill what is already dead. A zombie has already terminated and released its memory. The only way to remove a zombie is to prompt its parent to call wait(), or kill the parent process so the zombie is reparented to PID 1 and immediately reaped.

quick check

  • Where is an uninitialized global variable located in memory? In the BSS segment.
  • What register stores the base pointer to the active page directory in x86 CPUs? The CR3 register.
  • What does fork() return to the parent vs the child? It returns the child's PID ($>0$) to the parent, and returns $0$ to the child.

the 20-second summary

A process is an active instance of a program residing in virtual memory, segmented into Text, Data, BSS, Heap, and Stack. The kernel tracks each process via a Process Control Block (task_struct). Moving between processes requires a context switch—saving registers and swapping the CR3 page directory. Process creation uses fork() backed by lazy Copy-On-Write, and parents must reap deceased children via wait() to avoid exhausting the OS PID table with zombies.
