the 30-second elevator pitch

If a process is an entire restaurant (its own kitchen, pantry, and plumbing isolated from neighboring restaurants), then threads are multiple cooks working inside the exact same kitchen. They share the pantry (Heap, Global data, File descriptors), but each cook has their own hands (CPU registers), recipe bookmark (Program Counter), and personal notepad (Stack).

  • Why not just use processes? Creating a process is heavy: you copy page tables, initialize memory mappings, and pay a large context-switch penalty. Creating a thread is lightweight: you only allocate a new execution stack.
  • The Blessing and the Curse: Because threads share the same memory space, inter-thread communication takes 0 nanoseconds (just read a pointer). But because they share memory, if two threads write to the same counter at the same time without synchronization, your data gets corrupted.
🧷 remember
Threads within the same process share: Heap, Code (Text), Global data (BSS/Data), Open file descriptors, Environment variables.
Threads have strictly private: Thread ID (TID), Program Counter (PC), CPU registers, and private Stack.

threading models: 1:1 vs M:1 vs M:N

How do user-space programming languages map their high-level thread abstractions to real CPU cores managed by the OS kernel?

1:1 Kernel-Level Threads (Linux NPTL, C++, Java, Rust)

Every single user thread maps directly to one kernel thread managed by the OS scheduler.

  • Pros: True hardware parallelism. If you have 16 CPU cores, 16 threads execute simultaneously. Blocking on I/O doesn't freeze other threads.
  • Cons: High overhead. Every thread reserves a large stack (typically 2MB to 8MB in Linux/JVM). Context switching requires a mode transition into Ring 0. Scaling past 10,000 threads leads to thread-thrashing and memory exhaustion.

M:1 User-Level Threads (Classic Green Threads)

All user threads are managed inside the application runtime. The OS kernel only sees a single process running on one core.

  • Pros: Ultra-fast context switching (just saving CPU registers in userspace, ~10ns). Zero syscalls. Tiny stack footprint.
  • Cons: Fatal flaw: One blocking syscall blocks the entire universe. If one green thread calls read(), the kernel puts the whole OS process to sleep, stalling all other threads. No multi-core parallelism.

M:N Hybrid Model (Go Goroutines, Erlang, Java Loom)

Multiplexes $M$ lightweight user routines across $N$ kernel OS threads. The runtime acts as an in-process mini-operating system.

  • Pros: Best of both worlds. Goroutines start with just 2 KB of stack (grows dynamically). You can comfortably run 1,000,000 goroutines concurrently.
  • Cons: Complex runtime scheduling, work-stealing algorithms, and non-trivial preemption coordination.

deep dive: the Go scheduler (GMP model)

In senior systems interviews, Go's concurrency model is frequently referenced as the gold standard for high-concurrency runtimes:

  • G (Goroutine): The lightweight user routine. Contains its own 2KB stack and instruction pointer.
  • M (Machine): An OS kernel thread managed by the Linux scheduler.
  • P (Processor): A logical context representing a token to execute Go code. The number of Ps is capped at GOMAXPROCS (usually equal to the number of physical CPU cores).
  • Work-Stealing Scheduler: Each $P$ maintains its own local run-queue of Goroutines. If core 3 finishes all its Goroutines and becomes idle, it executes a work-stealing algorithm: it reaches into core 1's run-queue and steals half of its Goroutines to maintain 100% CPU utilization across all cores!

hardware realities: false sharing & cache line bouncing

Even if your code uses locks correctly, you can write multithreaded software that runs 10x slower on 16 cores than on 1 core. The culprit is False Sharing.

⚠️ gotcha: false sharing
CPUs never read or write individual bytes from RAM; they read data in fixed 64-byte Cache Lines.
If Core 1 updates counter_A and Core 2 updates counter_B, and both integers sit within the same 64-byte boundary, the hardware MESI Cache Coherency protocol forces Core 1 to invalidate Core 2's L1 cache line on every single write! The cache line furiously bounces back and forth across the CPU interconnect bus ("cache ping-pong"), killing throughput.
🔬 the false sharing fix: hardware cache padding
How systems engineers eliminate cache line contention:
  • The Root Cause: Two independent variables (e.g., counter_A and counter_B, 8 bytes each) placed next to each other in memory occupy the exact same 64-byte cache line. When Core 1 modifies A, Core 2's cache line for B is invalidated.
  • The Fix (Padding): Explicitly pad memory so each variable occupies its own dedicated 64-byte cache line. This completely isolates Cores 1 and 2, eliminating cache ping-pong and restoring linear multi-core scaling.

the golden formula: sizing thread pools for faang backend services

One of the most frequent system design interview questions: "How many threads should you configure in your backend service thread pool?"

Do NOT guess "50" or "100". Use the Little's Law / Goetz Thread Pool Formula:

$$N_{\text{threads}} = N_{\text{cpu}} \times U_{\text{cpu}} \times \left(1 + \frac{W}{C}\right)$$
  • $N_{\text{cpu}}$ = Number of available CPU cores.
  • $U_{\text{cpu}}$ = Target CPU utilization (usually 0.8 to 1.0).
  • $W$ = Wait Time (time spent blocked on database queries, network calls, disk I/O).
  • $C$ = Compute Time (time spent actively computing on the CPU).
🔬 worked example
You have an 8-core server. Your API endpoint handles a request in 100ms total: 95ms is spent waiting for PostgreSQL queries ($W = 95\text{ms}$), and 5ms is CPU JSON serialization ($C = 5\text{ms}$).
$$\frac{W}{C} = \frac{95}{5} = 19$$ $$N_{\text{threads}} = 8 \times 1 \times (1 + 19) = 8 \times 20 = \mathbf{160\text{ threads}}$$ If the workload were purely CPU-bound (e.g. video encoding, $W \approx 0$), optimal threads = $8 \times (1 + 0) = \mathbf{8\text{ threads}}$ (one thread per physical core to avoid context switch overhead).

quick check

  • If a thread crashes due to a null pointer dereference, what happens to other threads in that process? In C/C++, all sibling threads crash instantly because the OS delivers a fatal SIGSEGV to the entire process.
  • What is the default stack size for a thread in Linux/JVM vs a Go Goroutine? Linux/JVM is typically 2MB to 8MB; a Go Goroutine starts at just 2KB.
  • How do you prevent False Sharing in memory-sensitive multi-threaded code? Pad variables to align with the CPU's 64-byte cache line boundary.

the 20-second summary

Threads are lightweight streams of execution within a single process, sharing the heap, code, and file descriptors while keeping their own registers, program counter, and stack. Modern OSes use 1:1 kernel threads, while high-concurrency runtimes like Go employ M:N multiplexing with work-stealing schedulers to run millions of coroutines. On multi-core hardware, developers must guard against false sharing across 64-byte cache lines and size thread pools based on the I/O-to-CPU wait ratio.
