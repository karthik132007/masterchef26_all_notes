rag evaluation: measuring retrieval precision, recall, ranking, golden benchmarks & root-cause failure triage

why rag evaluation matters

If you don't evaluate RAG in two independent stages, you are debugging a dual-variable equation with one equation. You will blame the LLM for retriever sins, and blame the retriever for LLM hallucinations.

In Topic 07, we built a complete RAG pipeline: chunking documents, creating dense embeddings, running hybrid search with BM25, and reranking candidates. But when you test it in a Jupyter notebook with three questions, everything looks brilliant. Then you deploy to 5,000 users, and production falls apart:

  • The "Vibe Check" illusion: Manually testing 5 queries creates a dangerous false confidence. A subtle change in chunk size (e.g., dropping from 500 to 200 tokens) or tweaking your embedding model might improve 2 queries while silently breaking 40 others.
  • The Dual-Failure Dilemma: When a user receives an incorrect answer, there are two completely different failure origins:
    1. Retrieval failure: The retriever fetched the wrong chunks or missed the ground-truth document entirely. The LLM had zero evidence.
    2. Generation failure: The retriever fetched the exact ground-truth paragraph at Rank 1, but the LLM ignored it, hallucinated from its pre-training weights, or misread the numbers.
  • Garbage In, Garbage Out (GIGO): The smartest frontier model (Claude 3.5 Sonnet or GPT-4o) cannot answer accurately if the critical chunk was never retrieved. Retrieval sets the hard theoretical ceiling for overall system accuracy.
  • Token Cost & Latency Savings: Evaluating retrieval independently requires zero generative LLM API calls. You can benchmark 10,000 search queries in seconds using offline mathematical metrics without spending a cent on token generation.
🧷 the golden rule of rag evaluation
Never test your RAG pipeline end-to-end until your retriever passes its own benchmarks. If your retriever has a Recall@5 of 0.40, 60% of user questions will fail regardless of how brilliant your prompt engineering or LLM is.

retrieval evaluation

Retrieval evaluation treats the vector database and search algorithm like an Information Retrieval (IR) engine. Given a query $q$, the retriever searches through millions of chunks in corpus $D$ and returns an ordered list of $K$ candidate chunks:

$$\mathcal{R}_K = [d_1, d_2, \dots, d_K]$$

In standard machine learning classification, accuracy is simple: did you predict class 0 or 1? But in retrieval, we have massive class imbalance (10 relevant chunks hidden among 500,000 corpus chunks) and order dependency (a relevant chunk placed at Rank 1 is vastly more valuable than one buried at Rank 10).

To evaluate retrieval objectively, every query in your benchmark requires a set of Ground Truth Relevant Chunks $\mathcal{G}$ (chunks that genuinely contain the facts needed to answer the question). We then compare the retrieved list $\mathcal{R}_K$ against $\mathcal{G}$ using three foundational metrics:

Recall@K Completeness

Question: Did we catch all the relevant chunks needed to construct the complete answer?

Protects Against: Missing context, unanswered questions, and retrieval dropouts.

Precision@K Noise Control

Question: Out of the $K$ chunks we crammed into the prompt, how many were actually useful?

Protects Against: Context poisoning, bloated token costs, and LLM distraction.

MRR Rank Priority

Question: How close to the very top (Rank 1) was our very first relevant piece of evidence?

Protects Against: "Lost in the middle" attenuation and slow LLM attention scan.

recall@k

Recall@K measures coverage: of all the ground-truth chunks that contain the answer, what fraction did the retriever manage to catch in the top $K$ results?

$$\text{Recall@K} = \frac{|\mathcal{R}_K \cap \mathcal{G}|}{|\mathcal{G}|} = \frac{\text{Number of Relevant Chunks in Top } K}{\text{Total Number of Ground Truth Relevant Chunks}}$$
  • The denominator is $|\mathcal{G}|$ (Total Relevant Chunks in the corpus): It does not matter how large your entire database is; it only matters how many total chunks contain the necessary facts for this specific question.
  • Range: Always between $0.0$ (complete retrieval failure) and $1.0$ (100% of all required evidence retrieved).
  • The ceiling effect: If $\text{Recall@K} < 1.0$, information was lost. If a question requires 3 distinct facts (e.g. refund percentage, cut-off timeline, exceptions) spread across 3 chunks, and Recall@K is $0.33$, the LLM is literally missing 66% of the answer.

concrete worked example: recall@k step-by-step

Let's walk through an enterprise scenario. A user asks:

User Query: "What are the cancellation penalties, refund processing times, and medical emergency waivers for international flights?"

In your knowledge base, there are exactly 4 ground truth chunks ($|\mathcal{G}| = 4$) that contain these specific policies:

  • Doc A (Chunk #101): International cancellation penalty tier schedule.
  • Doc B (Chunk #102): 48-hour cut-off refund processing timelines.
  • Doc C (Chunk #103): Medical emergency fee waiver policy.
  • Doc D (Chunk #104): Natural disaster & force majeure flight exceptions.

Now, let's observe what happens when your vector database returns the top $K=5$ candidates:

Rank Retrieved Chunk Relevance to Query? Status
#1 Doc A (Chunk #101) Relevant Cancellation penalties ✅ Hit (1st relevant)
#2 Doc X (Chunk #890) Irrelevant Domestic carry-on luggage sizes ❌ Distractor
#3 Doc B (Chunk #102) Relevant Refund processing times ✅ Hit (2nd relevant)
#4 Doc Y (Chunk #441) Irrelevant In-flight meal booking rules ❌ Distractor
#5 Doc Z (Chunk #722) Irrelevant Frequent flyer lounge access ❌ Distractor

Let's calculate Recall@5:

$$\text{Relevant in Top 5} = \{\text{Doc A}, \text{Doc B}\} = 2$$ $$\text{Total Ground Truth Relevant Chunks} = \{\text{Doc A}, \text{Doc B}, \text{Doc C}, \text{Doc D}\} = 4$$ $$\text{Recall@5} = \frac{2}{4} = \mathbf{0.50}\quad (50\%)$$

Consequence for the user: The LLM receives Doc A and Doc B, so it successfully explains penalties and refund timelines. But because Doc C (medical waivers) was missed, the LLM tells the customer "Medical waivers are not offered under our policy" or simply hallucinates one!

what happens if we increase $K$ from 5 to 10?

Suppose expanding the search window to $K=10$ catches Doc C at Rank #7. Now we have retrieved 3 out of 4 relevant chunks:

$$\text{Recall@10} = \frac{3}{4} = \mathbf{0.75}\quad (75\%)$$

Recall increased! But what happened to precision and prompt noise? Let's analyze Precision next.

precision@k

Precision@K measures signal density: out of the $K$ chunks retrieved and stuffed into the prompt, what proportion is actual relevant signal rather than irrelevant junk?

$$\text{Precision@K} = \frac{|\mathcal{R}_K \cap \mathcal{G}|}{K} = \frac{\text{Number of Relevant Chunks in Top } K}{K}$$
  • The denominator is $K$ (Total chunks fetched): Precision penalizes you every time you fetch a useless distractor document.
  • Range: Between $0.0$ (100% noise) and $1.0$ (100% pure signal; every retrieved chunk is relevant).
  • Why Precision@K matters for LLMs:
    1. Context Poisoning: LLMs can be easily distracted by irrelevant text that shares incidental keywords with the query.
    2. Lost-in-the-Middle Penalty: The more noise chunks you pass, the harder it is for the model's self-attention to spot the true facts.
    3. Token Billing: If each chunk is 400 tokens, retrieving 10 chunks sends 4,000 tokens per prompt. If 8 of them are junk, 3,200 tokens ($80\%$ of your bill) are thrown directly into the trash.

concrete worked example: precision@k step-by-step

Revisiting the exact same 5 chunks retrieved above:

  • Retrieved at $K=5$: [Doc A ✅, Doc X ❌, Doc B ✅, Doc Y ❌, Doc Z ❌]
  • Number of relevant hits in top-5 = $2$ (Doc A, Doc B).
  • Total items evaluated $K$ = $5$.
$$\text{Precision@5} = \frac{2}{5} = \mathbf{0.40}\quad (40\%)$$

Interpretation: Only $40\%$ of the context window injected into the LLM contains real evidence. $60\%$ is useless noise (carry-on bags, meal bookings, lounge rules) that the LLM must sift through.

example 2: the effect of a cross-encoder reranker

Now suppose we deploy a Cross-Encoder Reranker (like bge-reranker-large) after vector retrieval. The reranker computes deep query-document cross-attention, throws out the irrelevant luggage and meal chunks, and pulls the top-3 most confident chunks:

Rank Reranked Chunk Relevance Status
#1 Doc A (Chunk #101) Cancellation penalty schedules ✅ Hit
#2 Doc B (Chunk #102) Refund processing timelines ✅ Hit
#3 Doc C (Chunk #103) Medical emergency waiver policy ✅ Hit

Let's calculate Precision@3 on this cleaned result:

$$\text{Precision@3} = \frac{3}{3} = \mathbf{1.00}\quad (100\%)$$

Every single token passed to the LLM is pure, validated signal. The prompt is compact, latency is halved, and the model cannot get distracted by baggage rules.

the fundamental precision@k vs recall@k trade-off

You cannot blindly optimize one without hurting the other. As you increase $K$:

Metric Formula Denominator Behavior when $K$ increases Failure when too low
Recall@K $\frac{|\mathcal{R}_K \cap \mathcal{G}|}{|\mathcal{G}|}$ $|\mathcal{G}|$ (Fixed Ground Truth) Always increases or stays flat (wider net catches more fish) Information Blindness: The LLM never sees the required facts and hallucinates.
Precision@K $\frac{|\mathcal{R}_K \cap \mathcal{G}|}{K}$ $K$ (Number of retrieved chunks) Almost always drops (pulls in marginal, low-relevance junk) Context Poisoning: The LLM drowns in distractors, driving up latency and cost.
🔬 production architectural fix: two-stage retrieval
How do top AI engineering teams win both? Two-stage retrieval:
  1. Stage 1 (Bi-Encoder Dense + BM25): Retrieve $K=50$ candidates. High $K$ guarantees high Recall ($> 95\%$).
  2. Stage 2 (Cross-Encoder Reranker): Score those 50 pairs and slice down to top $K=4$. The reranker compresses the list for high Precision ($> 85\%$) before prompt injection!

mrr (mean reciprocal rank)

Recall and Precision care only if a document was caught in the top $K$, but they are completely indifferent to position. Finding the answer at Rank 1 scores the exact same Precision@5 as finding it at Rank 5!

In real-world RAG, position is everything. Chunks at Rank 1 receive the highest attention weights from the LLM, whereas chunks at Rank 5 or Rank 8 suffer from the Lost-in-the-Middle phenomenon. Furthermore, in search bars and question-answering systems, users want the correct answer immediately.

MRR (Mean Reciprocal Rank) evaluates how high the FIRST relevant chunk is placed.

the reciprocal rank (rr) formula

For a single query $i$, the Reciprocal Rank ($\text{RR}_i$) is simply the multiplicative inverse of the rank of the first relevant document:

$$\text{RR}_i = \frac{1}{\text{rank}_i}$$
  • If the first relevant document is at Rank 1: $\text{RR} = \frac{1}{1} = \mathbf{1.0}$ (Perfect score).
  • If the first relevant document is at Rank 2: $\text{RR} = \frac{1}{2} = \mathbf{0.50}$.
  • If the first relevant document is at Rank 5: $\text{RR} = \frac{1}{5} = \mathbf{0.20}$.
  • If no relevant document appears in the top $K$: $\text{RR} = \mathbf{0.0}$.

mean reciprocal rank (mrr) across the test dataset

To evaluate your retriever across a benchmark test set of $|Q|$ queries, calculate the average Reciprocal Rank:

$$\text{MRR} = \frac{1}{|Q|} \sum_{i=1}^{|Q|} \frac{1}{\text{rank}_i}$$

concrete worked example: calculating mrr across 4 queries

Imagine evaluating an enterprise IT support RAG system on 4 diverse employee queries with $K=5$:

Query ID User Query Rank of 1st Relevant Chunk Reciprocal Rank (RR) Notes
Q1 "How do I reset my VPN password?" Rank 1 $\frac{1}{1} = \mathbf{1.00}$ Instant match at the very top.
Q2 "What is the maximum limit for 401k match?" Rank 3 $\frac{1}{3} \approx \mathbf{0.333}$ Two unrelated tax forms ranked above it.
Q3 "Where do I download Docker desktop license?" Rank 2 $\frac{1}{2} = \mathbf{0.50}$ Ranked just below general dev guidelines.
Q4 "SAML 2.0 IdP metadata entity ID configuration" None in Top 5 $\mathbf{0.00}$ Complete retrieval miss (Zero recall).

Now, calculate the system-wide MRR:

$$\text{MRR} = \frac{1.00 + 0.333 + 0.50 + 0.00}{4} = \frac{1.833}{4} = \mathbf{0.458}$$
⭐ interview question: when to use mrr vs ndcg?
  • Use MRR when there is one clear answer or winning chunk (e.g. fact lookup, known-item search, "What is our company tax ID?"). MRR only looks at the first relevant hit and ignores all subsequent hits.
  • Use NDCG (Normalized Discounted Cumulative Gain) when queries require multiple relevant chunks with varying degrees of importance (e.g., graded relevance: chunk A is essential (3), chunk B is supplemental (2), chunk C is tangential (1)).

golden answers

To compute Precision, Recall, MRR, or test whether the LLM hallucinated, you need an indisputable ground truth. In AI engineering, this benchmark dataset is called the Golden Dataset.

A true RAG Golden Dataset is not just a list of questions and answers. It consists of Ground Truth Triples:

$$\mathcal{T} = \Big( \text{Query},\; \mathcal{G}_{\text{context}},\; \mathcal{A}_{\text{golden}} \Big)$$
  1. $\text{Query}$: The realistic question asked by a user (including domain jargon, typos, or conversational phrasing).
  2. $\mathcal{G}_{\text{context}}$ (Golden Chunks): The exact chunk IDs or text spans in your knowledge base that contain the facts needed to answer. (Used to evaluate the Retriever).
  3. $\mathcal{A}_{\text{golden}}$ (Golden Answer): The verified, human-grade answer string. (Used to evaluate the Generator).

how to construct golden datasets

Method 1 Human Subject Matter Experts

Approach: Engineers or domain experts (doctors, lawyers, customer ops) write 100–500 realistic questions, highlight the exact source paragraphs, and craft reference answers.

Pros/Cons: 100% authoritative and trusted, but very expensive, slow to produce, and hard to scale when documents update.

Method 2 Synthetic Generation (Ragas / Auto-Eval)

Approach: An LLM (e.g. GPT-4o) reads your corpus chunks in reverse: for each chunk, it generates 3 diverse questions that can only be answered using that chunk.

Pros/Cons: Ultra-fast, produces thousands of triples for dollars, but can generate artificial queries that don't match human phrasing.

Method 3 Production Log Mining

Approach: Extract questions from production logs where users clicked "Copy answer" or gave a 👍 thumbs-up, verified by human review.

Pros/Cons: Captures genuine user query distributions, but requires an existing deployed system with user feedback loops.

evaluating generated answers against golden answers

Once your retriever fetches chunks and your LLM produces an answer $\hat{\mathcal{A}}$, how do you score $\hat{\mathcal{A}}$ against $\mathcal{A}_{\text{golden}}$?

  • Lexical Metrics (BLEU, ROUGE-L): Measures exact n-gram token overlap.
    Gotcha: Brittle! If the golden answer is "The fee is $50" and the LLM says "You will be charged fifty dollars", ROUGE gives a near-zero score despite 100% semantic accuracy.
  • Semantic Embedding Distance: Computes cosine similarity between $\text{embed}(\hat{\mathcal{A}})$ and $\text{embed}(\mathcal{A}_{\text{golden}})$. Captures paraphrasing, but can miss numerical inaccuracies ($50$ vs $500$).
  • LLM-as-a-Judge (The Modern Standard): Use an evaluator prompt with a strict rubric on an frontier model:
# Example LLM-as-a-Judge prompt for Golden Answer Verification
EVAL_PROMPT = """
You are an impartial evaluation judge. Compare the Student Answer to the Golden Reference Answer.
Score from 1 to 5 based strictly on factual agreement:
- 5: Completely accurate, covers all critical facts, zero contradictions.
- 3: Partially correct, misses minor details but has no false statements.
- 1: Contradicts golden answer or hallucinates false information.

User Query: {query}
Golden Reference: {golden_answer}
Student Answer: {student_answer}

Respond in strict JSON: {"score": <1-5>, "reason": "<explanation>"}
"""

failure analysis

When a RAG system fails, junior engineers immediately start rewriting system prompts or switching LLMs. Senior AI engineers perform a root-cause failure analysis across the pipeline.

Every RAG bug maps into one of four distinct failure archetypes in the RAG Diagnostic Matrix:

Failure Mode Observed Symptom Root Cause Engineering Fix
1. Retrieval Miss
Stage 1: Retriever		 $\text{Recall@K} = 0$. The ground truth chunk is completely absent from top-$K$. ● Chunk size too large (vector dilution)
● Keyword mismatch (BM25 missing)
● Embedding model blind to domain acronyms 		● Implement Hybrid Search (BM25 + Dense)
● Add HyDE (Hypothetical Document Embeddings)
● Use recursive semantic chunking with 15% overlap
2. Ranking Miss
Stage 1: Reranker		 $\text{Recall@K}$ is high, but $\text{MRR}$ is low. Golden chunk is buried at Rank 8–10. ● Bi-encoder cosine similarity scores noisy distractors slightly higher than true chunk
● "Lost in the Middle" attenuation 		● Deploy a Cross-Encoder Reranker
● Dynamically place highest-scored chunks at the very top and bottom of the context window
3. Faithfulness Failure
Stage 2: Generator		 Golden chunk is at Rank 1, but LLM output contradicts it or hallucinates external facts. ● Pre-training parametric bias overrides prompt
● Temperature is too high ($> 0.5$)
● System prompt allows speculative reasoning 		● Set temperature: 0.0
● System prompt: "Answer strictly and exclusively using the provided context. If not present, state 'NOT FOUND'"
● Require inline citations (e.g. [Doc 2])
4. Premature Refusal
Stage 2: Generator		 Relevant chunk is present in context, but LLM claims "I don't have enough information to answer." ● System prompt safety guardrail is overly aggressive
● Question phrased with slight synonym variance 		● Add few-shot examples demonstrating acceptable synthesis and inference over provided documents
● Calibrate guardrail prompts

summary & exam checklist

⭐ top rag evaluation interview questions
  • Why not just evaluate RAG with BLEU or ROUGE? Lexical overlap metrics penalize valid synonymous phrasing and cannot verify factual correctness or detect hallucinations. Use LLM-as-a-judge with deterministic retrieval metrics instead.
  • What is the difference between Recall@K and Precision@K in RAG? $$\text{Recall@K} = \frac{\text{Hits}}{|\mathcal{G}|} \quad (\text{Completeness ceiling}), \quad \text{Precision@K} = \frac{\text{Hits}}{K} \quad (\text{Signal density / Noise filter})$$
  • Why is MRR preferred for QA over Precision@K? In known-item search (e.g., finding the password reset link), you only care that the correct answer is at the very top. Finding extra relevant documents at positions 4 and 5 adds zero user value.
  • What is a Golden Dataset composed of? Ground truth triples: $\text{Query}$, $\mathcal{G}_{\text{context}}$ (the exact chunk IDs for retrieval evaluation), and $\mathcal{A}_{\text{golden}}$ (the human-verified answer for generation evaluation).
  • How do you debug an LLM that hallucinates despite correct context? Check temperature (drop to 0.0), strengthen system prompt constraints (strictly refuse ungrounded facts), and enforce inline citations per claim.
⚠️ common rookie mistake: tuning the llm before the retriever
If your retrieval Recall@5 is 0.45, spend 90% of your engineering time on chunking, hybrid BM25 search, metadata filtering, and cross-encoder rerankers. Tweaking prompt instructions when the context is missing is like repainting a car that has no engine.
