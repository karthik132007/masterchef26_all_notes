rag: open-book exams for llms, chunking, embeddings, and hybrid search

the 30-second idea

An LLM without RAG is taking a closed-book medical exam purely from memory. An LLM with RAG has an open library, a high-speed librarian, and precise page citations.

In Topic 06, we learned why LLMs hallucinate: their knowledge is frozen in parametric weights at training cutoff, and they optimize for linguistic plausibility rather than ground truth. Trying to cram an entire company wiki or database into the prompt causes context overflow, costs a fortune, and triggers the "Lost-in-the-Middle" phenomenon.

RAG (Retrieval-Augmented Generation) breaks the problem into two distinct engineering stages:

  1. Retrieve: Search an external knowledge store to fetch only the top few most relevant document chunks for the user's specific question.
  2. Generate: Inject those retrieved chunks directly into the LLM's context window as authoritative evidence, instructing the model to generate an answer grounded strictly in that evidence.
🧷 the simple idea behind rag
RAG = Search + Add to Prompt + Generate Answer.
Parametric memory (weights) supplies the reasoning and language fluency. Non-parametric memory (your docs index) supplies the fresh, checkable facts.

what is RAG?

Published originally by Lewis et al. (Meta AI, 2020), Retrieval-Augmented Generation transforms how AI systems access truth. Rather than retraining or fine-tuning weights whenever facts change, we decouple reasoning from factual storage.

Fine-Tuning Adapting Behavior

Purpose: Teaches the model a new style, tone, syntax, or task pattern (e.g., talk like a doctor, output strict JSON, code in Rust).

Weakness: Expensive, slow, risk of catastrophic forgetting, and struggles to memorize granular exact facts reliably.

RAG Dynamic Knowledge

Purpose: Equips the model with new knowledge (e.g., yesterday's sales figures, internal HR policies, user's private code repo).

Strength: Instant updates (just insert/delete vectors), zero retraining cost, 100% auditability with citations, and zero data leakage into weights.

chunking strategies

You cannot embed a 200-page PDF into a single vector. Why? Embedding models compress text into a fixed-length vector (e.g., 1536 floats). Trying to squeeze 100,000 words into 1,536 numbers causes semantic dilution — every nuance turns into an uninformative gray blur.

Conversely, if you embed each individual word, retrieval loses all surrounding context. Chunking is the art of finding the Goldilocks zone:

⚠️ Chunks Too Small (e.g. 50 tokens)

Problem: Sentences get severed mid-clause. Coreferences lose their subjects ("It crashed due to a timeout" — what is "It"?).

Impact: LLM receives disconnected fragments and hallucinates the missing connective tissue.

⚠️ Chunks Too Large (e.g. 2,000 tokens)

Problem: Embedding averages out multiple topics into one vector. Highly specific facts become invisible in vector space.

Impact: Top results return noisy irrelevant paragraphs, exhausting token budgets.

the core chunking strategies

1. Fixed-Size Character & Token Chunking

The simplest approach: cut text strictly every N characters or tokens (for example, every 500 characters). While trivial to implement, it frequently cuts right through sentences, words, and code blocks.

2. Recursive Character Splitting (Industry Standard)

Instead of cutting blindly, recursive splitters use a hierarchy of natural document delimiters:

separators = ["\n\n", "\n", " ", ""]

It first attempts to split by paragraphs (\n\n). If a paragraph exceeds the target chunk size, it splits that paragraph by lines (\n). If a line is still too long, it splits by words (" "), and only as a last resort splits characters. This keeps semantic units (paragraphs and sentences) intact wherever possible.

3. Semantic Chunking

Rather than relying on fixed character counts, semantic chunking watches for topic changes between sentences:

  1. Split the document into individual sentences.
  2. Compare the meaning of each sentence with the next one.
  3. When the topic clearly shifts, start a new chunk there.

Result: Every chunk holds one clear thought, no matter how long or short it is.

4. Sentence-Window & Parent-Document Retrieval

Addresses the retrieval-generation paradox: small chunks are best for search (high embedding precision), but large chunks are best for generation (rich context for the LLM).

  • Sentence-Window: Search using only 1 sentence. When that sentence matches the query, give the LLM a few sentences before and after it for context.
  • Parent-Document Retrieval: Keep big parent sections (around 1500 tokens) and small child pieces (around 200-300 tokens). Search over the small children. When a child matches, return its full parent to the LLM!
Strategy Chunk Size Compute Overhead Best Used For
Fixed-Size 300–500 tokens Minimal (Zero model calls) Quick prototypes, uniform raw text dumps
Recursive Character 400–800 tokens Very low (Regex only) General markdown, documentation, articles
Semantic Chunking Variable High (1 embedding call per sentence) Long analytical essays, transcripts, legal contracts
Parent-Document Child: 200t, Parent: 1500t Low–Medium Enterprise manuals, technical documentation, policies

chunk overlap

Imagine reading a mystery novel where page 42 ends with: "The detective discovered the murderer was", and page 43 starts with: "because of the fingerprints on the dagger." The crucial name was cut right across the page boundary!

This is the boundary problem. If a user asks "Who was the murderer?", neither page 42 nor page 43 has the complete semantic answer. The query vector will miss both chunks.

how overlap works in practice

Chunk overlap uses a sliding window: each new chunk reuses a little text from the end of the previous chunk.

If your chunk size is 500 tokens with a 50-token overlap, Chunk 1 covers tokens 0 to 500, Chunk 2 covers tokens 450 to 950, and so on. That repeated 50-token part protects sentences that sit on the border.

⭐ the 10%–20% golden rule
In practice, keeping overlap around 10% to 20% of the chunk size works well:
  • Too little overlap (under 5%): Sentences split across chunks still lose their context.
  • Too much overlap (over 30%): Storage grows, search returns duplicates, and embedding costs go up.

embeddings & vector space

In Topic 02, we saw embeddings as coordinates for meaning. In RAG, embeddings make semantic search possible.

An embedding model turns any text into a long list of numbers (a vector). For example, OpenAI's small model returns 1536 numbers per text. Texts with similar meaning get similar number-lists, even if they use completely different words.

🧷 semantic closeness
Sentences that mean the same thing end up close together in vector space, even if they share zero common words:
  • "The customer wants their money back"
  • "Initiate policy return reimbursement"
Both point in almost the same direction, so search treats them as a match.

fast search over millions of chunks (ann indexing)

When your store holds millions of chunks, checking every single one is too slow for chat. Vector databases use smart shortcuts (ANN indexes) to find close matches in milliseconds:

  • HNSW: A layered graph. Top layers jump quickly across topics; bottom layers fine-tune locally. Very fast, uses more memory.
  • IVF-PQ: Groups vectors into clusters and stores compressed versions. Very memory-friendly for huge collections.

how similarity works: meaning vs length

Once the query and the chunks are both turned into vectors, we need a simple way to decide which chunk is the closest match.

1. Compare direction, not length (cosine similarity)

Think of each vector as an arrow pointing in some direction. Cosine similarity simply asks: do these two arrows point the same way?

  • Same direction = same meaning = high score (close to 1).
  • Different direction = different meaning = low score.

Length is ignored on purpose, so a short summary and a long explanation of the same idea still match.

2. Why this beats plain distance for text

📐 Plain Distance

Measures straight-line distance between points.

Problem for text: Longer documents look farther away, even when they mean the same thing.

🎯 Direction Match

Measures only whether arrows point the same way.

Why it helps: A short summary and a long page about refunds point the same way, so they match well.

⚠️ handy shortcut used by databases
If vectors are pre-adjusted to the same length, this direction check becomes a simple fast multiply-and-add. That is why tools like Qdrant, Pinecone, and Chroma are so quick.

keyword search: TF-IDF & BM25

Dense vector search feels like magic until you search for an exact code. Vector search is weak at exact keywords.

If a customer searches for "ERR_404_SOCKET_RESET" or "SKU-99214-X", embedding models blur those into general ideas like "network error". They may return other socket errors and miss the exact code! This is where keyword (lexical) search wins.

1. TF-IDF idea in plain words

TF-IDF rewards words that are frequent in one doc but rare overall:

  1. Term Frequency: How often does the word appear in this document? More is better.
  2. Rarity across docs: How rare is the word overall? Common words like "the" or "is" get almost no points. Rare words like "osteosarcoma" or "EC2" get lots of points.

2. BM25 (the better TF-IDF)

BM25 is the standard keyword scorer used by Elasticsearch and Lucene. It fixes two simple problems:

  • Diminishing returns: Seeing "Kubernetes" 20 times is not 10x better than seeing it twice. Extra repeats give smaller and smaller bonus.
  • Fairness for length: A very long doc naturally has more matches. BM25 tones that down so long docs do not always win.

hybrid retrieval

Why choose between semantic intuition and keyword precision when you can run both? Hybrid Retrieval executes Dense Vector Search and Sparse BM25 Search in parallel, then fuses their results into one superior candidate list.

how do we combine both lists? (rank fusion)

Keyword scores and vector scores are on totally different scales, so we cannot just add them. The simple trick used everywhere is Reciprocal Rank Fusion (RRF): look only at rank positions, not raw scores.

Example: if Doc A is rank 1 in keyword search and rank 3 in vector search, it gets a high combined score because it did well in both lists. Docs that appear near the top in both lists jump to the very top, fixing the blind spots of each method.

summary & exam checklist

⭐ top exam & interview checklist
  • Parametric vs Non-Parametric: LLM weights are parametric (static, learned behaviors). Vector databases are non-parametric (dynamic, hot-swappable external facts).
  • Chunking Dilemma: Chunks that are too small lack semantic context; chunks that are too large cause vector dilution. Recursive splitting by paragraph and sentence is the standard baseline.
  • Chunk Overlap: 10%–20% overlap solves the boundary problem, preventing facts and sentence clauses from being severed across chunk splits.
  • Cosine Similarity vs Euclidean: Cosine similarity evaluates angle, making it invariant to document length. For pre-normalized vectors, cosine similarity is identical to dot product.
  • BM25 over TF-IDF: BM25 prevents keyword saturation via $k_1$ and prevents long document bias via $b$. Essential for error codes, SKUs, and exact terminology.
  • Why Hybrid + RRF: Combines semantic understanding (dense) with exact token match (sparse). RRF merges ranks without requiring brittle score calibration.
  • Bi-Encoder vs Cross-Encoder: Bi-encoders compute independent embeddings (fast $O(1)$ vector indexing). Cross-encoders compute full joint token cross-attention (slow $O(N)$, but ultra-accurate). Never search all docs with cross-encoders; use them only to rerank the top candidate pool.
⚠️ common production failure mode: the lost-in-the-middle trap
Even after reranking to top-5 chunks, do not blindly dump them in random order into the prompt! LLMs attend strongest to the very beginning and very end of the prompt context. Place your most critical retrieved evidence at the top and bottom of the context, not buried in the center.
