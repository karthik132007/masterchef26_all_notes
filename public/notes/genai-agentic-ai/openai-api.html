openai api · sdk architecture, completions, streaming, token economics & resilience

the 30-second idea

The OpenAI API is the universal HTTP contract of the Generative AI era.

Almost every modern model provider — whether proprietary like OpenAI and Anthropic, or open-source inference servers like vLLM, Ollama, Groq, Together, and DeepSeek — implements the exact same Chat Completions JSON schema. If you learn how to configure, stream, cost-optimize, and harden this API, you know how to talk to 95% of all LLMs on earth.

Building production applications with LLM APIs requires mastering four key components:

  • The Request Envelope: Navigating model, messages, temperature, top_p, and response_format (Structured Outputs).
  • Streaming & Latency: Eliminating multi-second freezes by streaming token chunks via Server-Sent Events (SSE).
  • API Economics: Understanding the 3x–4x price asymmetry between input and output tokens, leveraging prompt caching discounts, and avoiding budget bleed.
  • Production Resilience: Handling rate limits (HTTP 429 RPM/TPM), exponential backoff with jitter, and context overflow errors.
🧷 the lingua franca rule
You rarely need to rewrite client code when switching providers! You can switch from OpenAI to DeepSeek, Groq, or a local vLLM cluster simply by changing the base_url and api_key in your OpenAI() client.

the openai sdk: python architecture

The official openai SDK provides synchronous and asynchronous clients, typed response models, and automatic retries:

•••Python
from openai import OpenAI
import os

# Client automatically reads OPENAI_API_KEY from os.environ
client = OpenAI()

# Execute standard completion
response = client.chat.completions.create(
    model="gpt-4o",
    messages=[
        {"role": "system", "content": "You are an expert systems engineer. Respond concisely."},
        {"role": "user", "content": "Explain how Linux handles page faults in two sentences."}
    ],
    temperature=0.2,          # Low temperature = deterministic/factual
    max_tokens=150,           # Hard cutoff on output completion tokens
    top_p=0.95,               # Nucleus sampling cut-off
    presence_penalty=0.0,     # Encourages topic diversification
    frequency_penalty=0.0     # Penalizes literal word sequence repetition
)

# Extract content and token metadata
message_text = response.choices[0].message.content
usage = response.usage

print(message_text)
print(f"Prompt tokens: {usage.prompt_tokens} | Completion tokens: {usage.completion_tokens}")

Parameter Reference: The Levers of Generation

Parameter Type Default Engineering Function
model String Required Which model checkpoint to run (e.g. gpt-4o, gpt-4o-mini, deepseek-chat).
temperature Float [0.0 - 2.0] 1.0 Divides logits before softmax. 0.0 is greedy decoding (best for code/JSON); 0.7 is standard chat; >1.2 increases randomness.
top_p Float [0.0 - 1.0] 1.0 Nucleus sampling. The model considers only the smallest set of tokens whose cumulative probability exceeds top_p. Prefer altering either temperature or top_p, not both.
max_tokens Integer Model max Hard budget ceiling on generated output tokens. Generation halts when this count is reached even if the thought is incomplete.
response_format Object {"type": "text"} Set to {"type": "json_object"} or supply a Pydantic / JSON Schema for guaranteed valid structured parsing.
seed Integer None Setting a fixed seed best-effort guides the sampling engine to output deterministic results across identical prompts.

structured outputs: json schemas with zero hallucinations

Prior to Structured Outputs, engineers begged the model: "Output only valid JSON!". Models would inevitably hallucinate markdown ticks like ```json ... ``` or prepend conversational text like "Sure, here is your JSON:", breaking backend parsers.

Modern APIs offer Constrained Decoding (Grammar Masking): During inference, tokens that would violate the supplied JSON schema have their logits set to $-\infty$, mathematically guaranteeing 100% compliant JSON output!

•••Python (Pydantic Structured Output)
from pydantic import BaseModel, Field
from openai import OpenAI

class UserInfo(BaseModel):
    name: str
    age: int
    skills: list[str] = Field(description="Core technical proficiencies")

client = OpenAI()

completion = client.beta.chat.completions.parse(
    model="gpt-4o-mini",
    messages=[
        {"role": "user", "content": "Alex is a 28 year old engineer skilled in Python, Docker, and Kubernetes."}
    ],
    response_format=UserInfo
)

user: UserInfo = completion.choices[0].message.parsed
print(user.name)    # "Alex"
print(user.skills)  # ['Python', 'Docker', 'Kubernetes']

streaming: conquering latency (ttft)

Generating a 400-token paragraph at 40 tokens/second takes 10 full seconds. If your backend waits for the complete response before returning HTTP 200, users will stare at a spinner and abandon the application.

How Streaming Works Under the Hood (SSE)

When you set stream=True, the API does not close the HTTP connection. It responds with header Content-Type: text/event-stream and pushes chunks formatted as Server-Sent Events:

data: {"choices":[{"delta":{"content":"Linux"}}]}
data: {"choices":[{"delta":{"content":" handles"}}]}
data: {"choices":[{"delta":{"content":" page"}}]}
data: [DONE]

Python Streaming Implementation

•••Python (Streaming Generator)
from openai import OpenAI
import sys

client = OpenAI()

stream = client.chat.completions.create(
    model="gpt-4o-mini",
    messages=[{"role": "user", "content": "Write a short haiku about Linux daemons."}],
    stream=True
)

for chunk in stream:
    token = chunk.choices[0].delta.content
    if token is not None:
        sys.stdout.write(token)
        sys.stdout.flush()
print()

api costs & token economics

Cloud providers bill for LLM calls based on tokens consumed, standardized per 1,000,000 tokens ($/1M tokens).

The Asymmetry: Why Output Tokens Cost 3x–4x More

Input tokens and output tokens are not computationally equal on modern hardware:

Model Input Price / 1M Cached Input / 1M Output Price / 1M Cost Ratio (Out : In)
GPT-4o $2.50 $1.25 $10.00 4x
GPT-4o-mini $0.15 $0.075 $0.60 4x
Claude 3.5 Sonnet $3.00 $0.30 $15.00 5x
DeepSeek-V3 (MoE) $0.14 $0.014 $0.28 2x
⭐ why do output tokens cost so much more?
Input tokens are processed in parallel; output tokens are generated sequentially.
When processing 2,000 prompt tokens, the GPU runs self-attention across all 2,000 tokens concurrently in a single high-efficiency matrix multiplication pass. In contrast, generating 500 output tokens requires 500 sequential autoregressive steps — the entire model parameter weight matrix must be loaded into memory bandwidth registers 500 consecutive times!

Prompt Caching Discounts

When multiple API requests share the identical prompt prefix (such as a 4,000-token system prompt, API documentation, or reference code), the provider stores the KV-cache of those tokens in GPU memory. Subsequent calls matching that prefix qualify for automatic 50% to 90% prompt discounts and lower initial latency.

The Cost Formula

$$\text{Cost} = \left(\frac{N_{\text{uncached\_in}}}{10^6} \times P_{\text{in}}\right) + \left(\frac{N_{\text{cached\_in}}}{10^6} \times P_{\text{cache}}\right) + \left(\frac{N_{\text{out}}}{10^6} \times P_{\text{out}}\right)$$

5 Proven Production Cost Reduction Strategies

  1. Model Cascading & Routing: Route high-volume, simple tasks (intent detection, entity extraction) to efficient models like GPT-4o-mini or DeepSeek-V3 ($0.15/1M). Escalate only complex reasoning to GPT-4o.
  2. Cache-Optimized Prompt Structuring: Place static content (system prompt, few-shot examples) at the start of the prompt so prefixes remain identical across calls and hit prompt caches.
  3. Force Output Concision: Output tokens cost 4x more than inputs. Instruct the model: "Be succinct. Output only the requested code or JSON without conversational filler."
  4. Bound Output Tokens: Always configure max_tokens to prevent runaway generation when handling unexpected inputs.
  5. Async Batch API: For non-interactive workloads (evaluations, document ingestion, data labeling), submit queries via the Batch API for an automatic 50% discount.

production resilience: rate limits & retries

In production, API calls will fail. Network glitches, provider outages, and traffic spikes will trigger errors that your system must gracefully handle:

Status Code Error Meaning Root Cause & Remediation
429 Rate Limit Exceeded You exceeded RPM (Requests Per Minute) or TPM (Tokens Per Minute). Implement exponential backoff with random jitter.
400 Context Length Exceeded The combined input prompt plus requested max_tokens exceeds the model context window. Implement FIFO eviction or summarization.
401 Authentication Error Invalid API key, expired token, or incorrect organization header.
500 / 503 Server Overloaded OpenAI infrastructure experiencing high traffic. Retry after a backoff pause.
•••Python (Resilient Retry Loop)
import time
import random
from openai import OpenAI, RateLimitError, APIConnectionError

client = OpenAI()

def call_with_retry(messages, retries=3, base_delay=1.0):
    for attempt in range(retries):
        try:
            return client.chat.completions.create(
                model="gpt-4o-mini",
                messages=messages,
                timeout=15.0
            )
        except (RateLimitError, APIConnectionError) as e:
            if attempt == retries - 1:
                raise e
            # Full jitter backoff formula
            sleep_time = (base_delay * (2 ** attempt)) + random.uniform(0, 1)
            time.sleep(sleep_time)

developer cheat sheet & exam tips

⭐ exam recap: what you must remember
  • OpenAI Schema Universality: The messages=[{"role": ..., "content": ...}] structure is the universal standard adopted across closed and open-source inference servers alike.
  • Temperature vs. Top_P: Temperature adjusts the sharpness of logit distributions (use 0.0 for code/JSON); top_p applies nucleus probability filtering. Tune one, not both.
  • Structured Outputs: Constrained grammar decoding enforces valid JSON schemas directly at the token generation layer, preventing parsing failures.
  • Streaming (SSE): Reduces Time-To-First-Token (TTFT) from multi-second waits down to ~250 milliseconds by streaming delta chunks.
  • Cost Asymmetry: Output tokens cost 3x to 4x more than input tokens because outputs are memory-bandwidth bound and generated sequentially one token at a time.
  • Rate Limits: Always account for both Requests Per Minute (RPM) and Tokens Per Minute (TPM); handle HTTP 429 with exponential backoff and jitter.
