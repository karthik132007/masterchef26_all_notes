same web, faster roads — from one-at-a-time to many-at-once.

the 30-second idea

HTTP/1.1 sends requests one at a time over TCP. HTTP/2 sends many at once over the same TCP connection. HTTP/3 keeps that trick but swaps TCP for QUIC over UDP — so one slow request can no longer jam the whole road. HTTP/4 is still predicted, not real.

  • 1997 — HTTP/1.1: one road, traffic jams.
  • 2015 — HTTP/2: one road, multiple lanes (multiplexing).
  • 2022 — HTTP/3: a better road (QUIC) that handles bumps smoothly.
  • Future — HTTP/4: a smart, AI-driven highway. Predicted, not promised.
🧷 remember
The whole evolution is one sentence: 1.1 = sequential over TCP → 2 = multiplexed over TCP → 3 = multiplexed over QUIC/UDP. Everything else is detail.

HTTP/1.1 — one request at a time

  • Uses TCP, and mostly sends requests one after another (sequentially).
  • Head-of-Line (HOL) blocking: a slow first request blocks everything behind it, like one tractor holding up a single-lane road.
  • Text-based headers — readable, but bulky. Every request repeats them, so more overhead.
  • Simple and widely supported. Still fine for small, simple sites.

Bottom line: one request at a time over a single TCP connection — prone to delays (HOL blocking).

HTTP/2 — many at once, same road

  • Still uses TCP — the road didn't change, the driving did.
  • Multiplexing: multiple requests and responses travel over one TCP connection simultaneously.
  • Binary framing instead of plain text — machines parse it faster.
  • Header compression (HPACK) — stops resending the same bulky headers every time.
  • Noticeably faster than 1.1, especially pages loading many resources at once.

Bottom line: multiple requests and responses simultaneously over a single TCP connection. Better performance.

⚠️ gotcha
HTTP/2 multiplexes, but it still runs on TCP — so TCP-level HOL blocking survives. One lost packet still stalls every stream on that connection. Remember this; it is exactly what HTTP/3 was built to kill.

HTTP/3 — same trick, a bump-proof road

  • Uses QUIC instead of TCP — and QUIC runs over UDP.
  • Keeps HTTP/2-style multiplexing, but each stream is independent — no TCP-level HOL blocking between streams. One slow stream can't jam the others.
  • Faster connection setup (0-RTT on repeat visits — talking resumes almost instantly).
  • Built for mobile and unstable networks — switching from Wi-Fi to data mid-load doesn't kill everything.
  • TLS 1.3 is baked into QUIC, not bolted on beside it.

Bottom line: multiplexing over QUIC (UDP). No TCP-level HOL blocking. Fast, reliable, and great on shaky networks.

HTTP/4 — predicted, not real yet

Everything here is expected, not confirmed — say "predicted" in exams and interviews, or lose marks. The broad bet: it builds on HTTP/3's QUIC foundation and gets smarter everywhere.

  • Smarter connection management — better routing and connection reuse.
  • Advanced congestion control and better request prioritization.
  • Security beyond TLS 1.3 — post-quantum crypto is the headline guess.
  • More efficient header compression than QPACK.
  • Advanced queries and real-time communication, including real-time bi-directional streams.
  • AI/ML-optimized delivery and caching, plus improved edge delivery.

Bottom line: next-gen performance with smarter transport, real-time features, and AI-driven optimization — on paper, for now.

methods — same in every version

Versions changed the transport, not the verbs. These work identically on 1.1, 2 and 3.

⭐ exam tip
If asked to compare versions, write this trio and stop: 1.1 = sequential over TCP (HOL blocking) · 2 = multiplexed + HPACK over TCP (still TCP-level HOL) · 3 = multiplexed + QPACK over QUIC/UDP (HOL gone, TLS 1.3 inside). The comparison table below is your backup detail.

evolution timeline

in short

HTTP/1.1 → TCP → sequential requests → more delay. HTTP/2 → TCP + multiplexing → faster. HTTP/3 → QUIC/UDP + multiplexing → even faster and reliable. HTTP/4 → QUIC+ and smarter features → the future of the web, maybe.
