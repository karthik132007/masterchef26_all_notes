REST is not a protocol or a software package. It is an architectural philosophy that treats the web as a set of nouns manipulated by a fixed set of universal verbs.

the 30-second idea

REST (Representational State Transfer) is an architectural style for distributed systems defined by Roy Fielding in 2000. It organizes your system into addressable Resources identified by URIs, manipulated using standard HTTP verbs, and transferred via stateless representations (like JSON).

🍝 The Restaurant Menu Grammar Analogy

Imagine a restaurant where every customer invents their own messy grammar:

  • Customer 1 shouts: /cookMeAPastaNow
  • Customer 2 whispers: /removeTheSoupFromTheTable?plate=4
  • Customer 3 writes: /executeBillCreation()

The kitchen falls into complete anarchy. REST establishes a strict, universal grammar:

  • The Menu has only NOUNS (Resources): /pizzas, /pizzas/42, /tables/5/orders.
  • The Kitchen has only 4 standard VERBS (HTTP Methods):
    GET /pizzas/42 (Look at the pizza)
    POST /pizzas (Bake a new pizza)
    PUT /pizzas/42 (Replace the entire pizza with a new recipe)
    DELETE /pizzas/42 (Throw the pizza in the trash)
🧷 remember
URLs contain Nouns only (/users/12/orders). HTTP Verbs contain Actions (GET, POST, PUT, DELETE). Never put verbs in your URLs!

the safety vs idempotency 2x2 matrix

This is easily the single most frequent interview question on web architecture:

good rest vs bad rpc url design

Action❌ Bad RPC Style (Verbs in URL)✅ Clean RESTful Design (Noun + HTTP Verb)
Fetch all users GET /getAllUsers GET /users
Create a user POST /user/create POST /users
Update user profile POST /user/update?id=42 PUT /users/42 or PATCH /users/42
Delete an article GET /deleteArticle/99 (Catastrophic: Web crawlers will delete your DB!) DELETE /articles/99
Fetch user's orders GET /getUserOrders?userId=42 GET /users/42/orders (Hierarchical resource nesting)

making post requests safe: idempotency keys

Because POST /payments is not idempotent, what happens if a network hiccup occurs after the server charges the card but before the client receives the 200 OK response? If the client retries, the customer is billed twice!

Stripe invented the Idempotency-Key pattern to solve this:

POST /v1/charges HTTP/1.1
Host: api.stripe.com
Idempotency-Key: 9a7b-3c4d-unique-uuid-1234
Content-Type: application/json

{"amount": 5000, "currency": "usd"}

The server saves the UUID in Redis alongside the result. If a retry arrives with the exact same Idempotency-Key, the server skips payment processing and simply replays the cached response!
