HTTP was designed as a monologue: the client asks, the server answers. WebSocket transforms it into a two-way telephone call where both sides can talk simultaneously.

the 30-second idea

WebSocket (RFC 6455) is an application-layer protocol providing full-duplex, bidirectional communication channels over a single, persistent TCP connection.

  • The Half-Duplex HTTP Bottleneck: In standard HTTP, the server can never push data to you unprompted. To build a live crypto ticker or multiplayer game, developers had to resort to "polling" (asking the server every 500 ms: "Any updates? Any updates?"). This flooded networks with megabytes of redundant HTTP headers for mostly empty responses.
  • The WebSocket Revolution: A client initiates a standard HTTP request with an Upgrade: websocket header. If the server supports it, it replies with HTTP/1.1 101 Switching Protocols. At that exact microsecond, HTTP is discarded. The underlying TCP socket stays open, allowing both parties to exchange raw binary or text frames with as little as 2 to 6 bytes of header overhead per frame!
📞 The Postal Service vs The Open Direct Hotline
Imagine tracking live stock price fluctuations:
  • HTTP Polling (Postal Service): Every 2 seconds, you write a letter: "What is the price of Apple stock?", lick an envelope, pay for a postage stamp (500–1000 bytes of HTTP headers), and drop it in the mailbox. 99% of the time, the postman returns a letter saying: "No change." The waste in paper, stamps, and latency is colossal.
  • WebSocket (The Open Telephone Hotline): You send one initial letter saying: "Let's get on an open telephone call." The server agrees (HTTP 101). You both pick up the receiver. Envelopes and stamps are thrown in the trash. You both listen and speak freely whenever an event happens with zero waiting and zero wasted packaging!
🧷 remember
Full-Duplex: Both client and server can transmit messages concurrently at any time without waiting for a request or response. Schemes: ws:// (unencrypted, port 80) and wss:// (encrypted over TLS, port 443).

animated handshake & bidirectional frame stream

inside the upgrade handshake: the magic guid

To prevent non-WebSocket caching proxies from caching an upgrade response, WebSocket uses a cryptographic handshake challenge:

GET /socket.io/ HTTP/1.1
Host: api.binance.com
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Key: dGhlIHNhbXBsZSBub25jZQ==
Sec-WebSocket-Version: 13

The server takes the client's 16-byte random key, appends the universally standardized magic GUID 258EAFA5-E914-47DA-95CA-C5AB0DC85B11, computes the SHA-1 hash, base64 encodes it, and returns it:

HTTP/1.1 101 Switching Protocols
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Accept: s3pPLMBiTxaQ9kYGzzhZRbK+xOo=

the binary frame anatomy (rfc 6455)

Unlike HTTP's verbose ASCII headers, WebSocket encodes frames with bit-level precision:

  • FIN (1 bit): Indicates if this is the final fragment of a large message.
  • Opcode (4 bits): 0x1 (UTF-8 Text), 0x2 (Binary Data), 0x8 (Connection Close), 0x9 (Ping Heartbeat), 0xA (Pong Heartbeat).
  • MASK bit (1 bit): MUST be 1 for all client-to-server frames! The client XORs the payload with a random 4-byte key.

horizontal scaling: the pub/sub backplane

Because WebSockets are stateful, long-lived TCP connections, they do not scale horizontally with standard round-robin load balancers:

If User A connects to Server 1 and User B connects to Server 2, how does Server 1 deliver User A's chat message to User B? You need a Message Broker backplane (Redis Pub/Sub, RabbitMQ, or Kafka). When Server 1 receives a message, it publishes to a Redis channel; Server 2 subscribes to the channel and pushes the frame down User B's active socket.

  https://echo.websocket.events/.ws
⚠️ the 60-second load balancer idle drop
Cloud load balancers (AWS ALB, GCP Cloud Load Balancing, Nginx) enforce default idle connection timeouts (typically 60 seconds). Because WebSockets can remain idle when users aren't typing, the load balancer will silently terminate the TCP connection unless you implement periodic Ping/Pong heartbeats every 20–30 seconds!
⭐ viva & interview question
Q: Why does RFC 6455 mandate that clients MUST mask all frames with a random 4-byte key, while server frames MUST NOT be masked?
A: To prevent Cache Poisoning Attacks on transparent corporate proxies.
In the early days of WebSockets, malicious scripts running in a browser could craft raw byte sequences resembling standard HTTP requests (e.g. GET /bank.js HTTP/1.1). Transparent, misconfigured corporate caching proxies in between might misinterpret these bytes inside a TCP stream as genuine HTTP requests and cache malicious responses, poisoning the cache for all employees. By forcing the client to XOR payload bytes with a random 4-byte key unknown to the browser script, the byte patterns appearing on the wire are completely randomized, making it impossible to trick intermediate proxies. The server doesn't need to mask responses because the client cannot be an attacker tricking its own outbound proxy.
