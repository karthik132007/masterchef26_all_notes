REST with JSON is built for human readability and public web browsers. gRPC with Protobuf is engineered for high-throughput microservices that need to squeeze every microsecond out of the CPU and wire.

the 30-second idea

gRPC is an open-source, high-performance Remote Procedure Call (RPC) framework created by Google. It allows a client application to directly invoke a method on a server application running on a completely different physical machine as if it were a local in-memory function call.

  • The Two Architectural Pillars:
    1. Protocol Buffers (Protobuf): Replaces human-readable, repetitive text JSON with an ultra-compact, strongly-typed binary serialization format.
    2. HTTP/2 Transport: Replaces single-request HTTP/1.1 connections with multiplexed, bidirectional binary streams over a single persistent TCP connection.
  • The Real-World Speedup: In production microservice meshes, Protobuf payloads are 5x to 10x smaller on the wire than JSON, and serialize/deserialize 7x to 10x faster on CPU because Protobuf completely avoids string parsing!
📜 The Formal Written Letter vs The Military Radio Codebook
Imagine commanding a remote field unit to take action:
  • REST + JSON (The Formal Letter): You mail a typed document: {"action": "fire_artillery", "target_coordinates": {"latitude": 45.123, "longitude": -73.456}, "round_type": "smoke"}. It is easy for any civilian to read, but printing, folding envelopes, licking stamps, and parsing every quotation mark and bracket character by character wastes enormous time and CPU cycles.
  • gRPC + Protobuf (The Pre-Shared Codebook): Both units already hold an identical codebook (the compiled .proto contract). Over the radio, you simply transmit a tiny binary sequence: Tag 1: 45.123 | Tag 2: -73.456 | Tag 3: 2. The receiver maps numbers to offsets in nanoseconds. Zero repeated field names, zero string parsing, executed at line speed!
🧷 remember
gRPC = HTTP/2 (Multiplexed Streams) + Protocol Buffers (Binary Serialization) + Code Generation (Type-Safe Stubs in Go, Java, Python, Rust, C++).

the 4 rpc communication patterns

the protobuf schema contract (.proto)

In gRPC, everything starts with an Interface Definition Language (IDL) file. Both client and server compile this file to generate native, compile-time type-safe code in their respective programming languages:

syntax = "proto3";

package payment;

service PaymentService {
    // 1. Unary RPC (Single request, single response)
    rpc ProcessPayment (PaymentRequest) returns (PaymentResponse);

    // 2. Server Streaming (Single request, continuous response stream)
    rpc StreamTransactions (AccountRequest) returns (stream Transaction);

    // 3. Client Streaming (Continuous upload stream, single confirmation)
    rpc UploadMetrics (stream Metric) returns (UploadSummary);

    // 4. Bidirectional Streaming (Both sides stream concurrently)
    rpc ChatRoom (stream Message) returns (stream Message);
}

message PaymentRequest {
    int64 user_id = 1;     // Tag 1 (1 byte wire header)
    double amount = 2;     // Tag 2
    string currency = 3;   // Tag 3
}

rest vs grpc architectural decision matrix

FeatureREST (HTTP/1.1 + JSON)gRPC (HTTP/2 + Protobuf)
Primary Domain Public APIs, third-party developers, browser frontends. Internal East-West microservices, low-latency service meshes.
Browser Support Native: Every browser speaks fetch() out of the box. Requires Proxy (gRPC-Web): Browsers cannot access raw HTTP/2 frames.
Payload Efficiency Bulky text format with repeated field keys and escape characters. Ultra-Compact binary: 5x to 10x smaller wire footprint.
CPU Overhead Heavy string scanning, regex tokenization, UTF-8 parsing. Minimal: Direct byte-level memory mapping without string parsing.
Contract Rigidity Loose: JSON schemas drift, optional fields often break runtimes. Strict: Code generated at compile time; impossible to mismatch types.

how to inspect and test grpc from your terminal

# List all available services on a gRPC server using grpcurl (like curl for gRPC)
grpcurl -plaintext localhost:50051 list

# Describe the methods and message types in a service
grpcurl -plaintext localhost:50051 describe payment.PaymentService

# Invoke a gRPC method directly from your command line with JSON input
grpcurl -plaintext -d '{"user_id": 101, "amount": 99.50, "currency": "USD"}' \
  localhost:50051 payment.PaymentService/ProcessPayment

# Compile a .proto file into Go client/server stubs
protoc --go_out=. --go-grpc_out=. payment.proto
⚠️ the layer 4 load balancing disaster in grpc
Because gRPC runs on persistent HTTP/2 connections, it creates one single TCP socket between the client and the server. If you place a standard Layer 4 (TCP) load balancer (like an AWS NLB or standard Kubernetes ClusterIP) in front of your service, all traffic from that client will stick to ONE backend pod indefinitely, leaving all other pods completely idle!
The Solution: You MUST use either:
  1. Layer 7 Reverse Proxy (Envoy, Traefik, AWS ALB): Terminates HTTP/2 and balances individual RPC streams.
  2. Client-Side Load Balancing: The client resolves all pod IPs via DNS/k8s headless service and round-robins RPC calls internally across warm sockets.
⭐ viva & interview question
Q: How does Protocol Buffers maintain backwards and forwards compatibility when schemas evolve? What are the cardinal rules of field tags?
A: Protobuf matches fields on the wire purely by their integer tag numbers (1, 2, 3), never by field name.
  • Rule 1: NEVER change or reuse a field tag number. If you delete int64 user_id = 1;, tag 1 must be marked as reserved 1;. If a new developer later assigns tag 1 to a string field, older clients reading the message will experience silent, catastrophic data corruption!
  • Forward Compatibility: When a newer client sends a message containing newly added tags to an older server, the older server simply preserves the unknown tags in an unknownFields buffer without throwing errors, passing them along intact.
