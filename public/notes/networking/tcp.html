a phone call, not a postcard — hello first, then talk.

the 30-second idea

TCP delivers your data reliably, in order, over an unreliable network. Before a single byte of your message moves, both sides shake hands and agree on the rules. After that, every byte is numbered, confirmed, and re-sent if lost.

  • The dumb-proof version: UDP is a postcard — you drop it in the box and hope. TCP is a phone call — "hello? can you hear me? yes? okay, listen…" and if a sentence breaks up, you repeat it.
  • TCP lives at OSI layer 4, on top of IP's best-effort delivery. IP finds the road; TCP makes sure everything arrives intact.
🧷 remember
No handshake, no talking. SYN → SYN-ACK → ACK opens every TCP conversation on the internet — including the one loading this page.

the 3-way handshake — the most drawn diagram in networking

why three steps — one line each

  • 1 · SYN (seq=x) — "can you hear me? I'll count from x."
  • 2 · SYN-ACK (seq=y, ack=x+1) — "loud and clear! I'll count from y, and I got your x."
  • 3 · ACK (ack=y+1) — "got your y too. We're connected — talk."

Two messages couldn't do it: both sides must prove they can send AND receive, and both must agree on a starting number. That is why it is three, not two.

how TCP keeps its promises

The handshake only opens the door. These four habits keep every byte safe after it:

  • Sequence numbers — every byte is numbered, so the receiver reassembles them in order even if they arrive shuffled.
  • ACKs + retransmission — no confirmation before the timer runs out? Send it again. Watch it happen:
  • Checksums — every segment carries a fingerprint. Arrived damaged? Treated as lost: re-sent.
  • Flow control (sliding window) — the receiver says "my bucket holds this much", and the sender never pours faster. No drowning slow devices.
  • Congestion control — same idea, but for the network itself: start slow, speed up while the road is clear, back off at the first jam.

hanging up — the 4-step goodbye

Connections close politely, from both sides: FIN → ACK → FIN → ACK. Each side says "I'm done sending", and the other confirms. A handshake to open, a mirrored handshake to close.

what's inside the header — 4 things that matter

  • Ports — which app on each side (e.g. 443 for HTTPS). The address gets you to the building; the port gets you to the flat.
  • Sequence + ACK numbers — the counting system behind ordering and confirmations.
  • Flags — single-bit signals: SYN (start), ACK (confirm), FIN (finish).
  • Window size — the "my bucket is this big" number that drives flow control.

⭐ exam tip
Draw the handshake with numbers: SYN (seq=x) → SYN-ACK (seq=y, ack=x+1) → ACK (ack=y+1). Then one line: reliable + ordered + connection-oriented; uses ACKs, retransmission and flow control. Full marks.
⚠️ gotcha
HTTP never meets UDP directly in classic stacks — your HTTP/1.1 and HTTP/2 requests ride TCP (that's the handshake you pay before every connection). DNS uses UDP precisely because one tiny question-answer pair isn't worth handshaking over. And UDP has no handshake at all — nothing to draw.

quick check

  • Why can't the handshake be 2 steps? Because both sides must confirm both directions and agree on starting sequence numbers. Step 3 is the client's proof back.
  • Packet 5 of 10 vanishes. What does the user notice? Nothing — no ACK arrives, the timer fires, packet 5 is re-sent, and the stream stays perfectly ordered.
  • Video call or file download — which gets TCP? The download. The call takes UDP: a late pixel is useless, but a missing byte in a file is fatal.

the 20-second answer

TCP gives reliable, ordered delivery over IP's unreliable service. It opens with SYN, SYN-ACK, ACK — agreeing on sequence numbers both ways — then numbers every byte, confirms with ACKs, re-sends what goes missing, and paces itself with flow and congestion control. Slower than UDP, and safe on purpose.
