clients should not be forced to depend on interfaces they do not use — build lean role interfaces over bloated monoliths.

the core intuition

The Interface Segregation Principle (ISP) states:

"Clients should not be forced to depend upon methods that they do not use."

When an interface becomes a catch-all "fat interface" containing every possible method a system might ever need, every class that implements that interface becomes tightly coupled to methods it doesn't care about.

🧷 the remote control mental model
Imagine a universal television remote control with 120 buttons: DVD playback, VCR rewinding, picture-in-picture, and 3D glasses sync. If all you want to do is stream a movie on Netflix, you only need Power, Volume, and Navigation.

A bloated interface forces simple devices to carry all 120 buttons. ISP advises providing focused, modular controls: a PowerController, an AudioController, and a NavigationController.

why fat interfaces poison codebases

  • Stub Pollution: Classes implementing the interface are cluttered with dummy stub methods:
    ● ● ●python — code smell: empty stub method
    def fax_document(self, doc):
    pass  # Not supported, but required by interface!
  • Unwanted Recompilation / Redeployment: In compiled languages (C++, Java, Go), if method Z() is added to an interface, all 40 classes implementing that interface must be modified and recompiled — even if 39 of them never call Z().
  • Violates the Principle of Least Privilege: A client that only needs read access is handed an object with write(), delete(), and purge_all() methods, increasing the risk of misuse and security vulnerabilities.

the violation: the monolithic multi-function machine

Consider an office hardware interface that groups printing, scanning, faxing, and stapling into a single interface:

● ● ●python — anti-pattern: fat multi-function interface
# ANTI-PATTERN: Fat Interface Violates ISP
from abc import ABC, abstractmethod

class Machine(ABC):
    @abstractmethod
    def print_document(self, document: str) -> None:
        pass

    @abstractmethod
    def scan_document(self) -> str:
        pass

    @abstractmethod
    def fax_document(self, document: str, number: str) -> None:
        pass

    @abstractmethod
    def staple_document(self, document: str) -> None:
        pass


# A simple $50 economic home printer only knows how to print ink on paper!
class BudgetHomePrinter(Machine):
    def print_document(self, document: str) -> None:
        print(f"[BudgetPrinter] Printing: {document}")

    # Forced to provide empty or dummy implementations for irrelevant operations:
    def scan_document(self) -> str:
        raise NotImplementedError("This budget model cannot scan!")

    def fax_document(self, document: str, number: str) -> None:
        raise NotImplementedError("This budget model cannot fax!")

    def staple_document(self, document: str) -> None:
        raise NotImplementedError("This budget model cannot staple!")
⚠️ notice the overlap between isp and lsp
Fat interfaces are the number one cause of LSP violations! When an interface forces classes to implement methods they cannot support, developers resort to raising NotImplementedError — instantly breaking Liskov substitutability.

the clean architecture refactor: role interfaces

Following Martin Fowler's Role Interface pattern, we decompose the fat interface into distinct, single-purpose capabilities. In modern Python, we can define these using typing.Protocol (structural subtyping) or abc.ABC:

● ● ●python — clean architecture: fine-grained role protocols
# CLEAN ARCHITECTURE: Role Interfaces via Python Protocols (ISP Compliant)
from typing import Protocol

# 1. Fine-grained, focused role protocols
class Printable(Protocol):
    def print_document(self, document: str) -> None:
        ...

class Scannable(Protocol):
    def scan_document(self) -> str:
        ...

class Faxable(Protocol):
    def fax_document(self, document: str, number: str) -> None:
        ...

class Stapleable(Protocol):
    def staple_document(self, document: str) -> None:
        ...


# 2. Simple devices only implement what they actually do (Zero boilerplate!)
class BudgetHomePrinter:
    def print_document(self, document: str) -> None:
        print(f"[BudgetPrinter] Printing: {document}")


# 3. High-end industrial devices compose multiple roles cleanly
class EnterprisePhotocopier:
    def print_document(self, document: str) -> None:
        print(f"[EnterpriseCopier] High-speed laser printing: {document}")

    def scan_document(self) -> str:
        print("[EnterpriseCopier] 1200 DPI optical scanning complete.")
        return "Scanned PDF payload"

    def fax_document(self, document: str, number: str) -> None:
        print(f"[EnterpriseCopier] Faxing to {number}")

    def staple_document(self, document: str) -> None:
        print("[EnterpriseCopier] Mechanical stapling applied to corners.")


# 4. Client services depend strictly on the narrow role they require!
class DocumentPrintingService:
    """This service only cares about printing — scanning/faxing are irrelevant!"""
    def __init__(self, printer: Printable):
        self.printer = printer

    def execute_print_job(self, doc: str) -> None:
        self.printer.print_document(doc)

# Both work seamlessly without unexpected runtime exceptions:
svc1 = DocumentPrintingService(BudgetHomePrinter())
svc1.execute_print_job("Monthly_Report.pdf")

svc2 = DocumentPrintingService(EnterprisePhotocopier())
svc2.execute_print_job("Architectural_Blueprint.pdf")

isp in dynamic vs statically typed languages

ParadigmMechanismHow ISP is Enforced
Go Single-method interfaces (e.g. io.Reader, io.Writer, io.Closer) Implicit satisfaction. Packages export interfaces with 1-2 methods; structs satisfy them automatically.
Java / C# Interface inheritance & default methods Classes implement multiple small interfaces (e.g. implements AutoCloseable, Serializable).
Python Duck Typing & typing.Protocol (PEP 544) Static type checkers (MyPy, Pyright) verify that passed objects possess the exact required methods at type-check time.
⭐ machine coding interview tip: repository design
A frequent interview design problem is: "Design a Data Access Layer / Repository."
Do not create a single mega-interface: CrudRepository: create(), read(), update(), delete(), search(), export_csv(), bulk_insert().

Segregate into roles:
  • Reader[T]: get_by_id(id) -> T
  • Writer[T]: save(entity: T) -> None
  • Searchable[T]: find_by_query(query) -> list[T]
Now, cached read replicas only implement Reader, whereas read-only background audit services cannot accidentally call delete().
