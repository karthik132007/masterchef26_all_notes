open for extension, closed for modification — plug new capabilities into existing architectures without modifying tested code.

the core intuition

The Open/Closed Principle (OCP) was originally defined by Bertrand Meyer in 1988 and later refined by Robert C. Martin. It states:

"Software entities (classes, modules, functions) should be open for extension, but closed for modification."
🧷 the hardware plug mental model
Consider the electrical wall socket in your home or the USB-C port on your laptop:
  • The socket interface is closed for modification: you never rip open your drywall or solder your laptop's motherboard to plug in a new device.
  • It is open for extension: you can plug in a phone charger, a lamp, a monitor, or an electric guitar without altering the socket's physical circuitry.
In software, abstractions (interfaces, base classes, protocols) serve as the sockets; new features serve as the plugs.

code smells: how to spot ocp violations

  • The Infinite Switch / Conditional Cascade: Chains of if/elif/else or switch statements checking a type tag or enum:
    ● ● ●python — code smell: branching on type tags
    if payment_type == "credit_card":
    ...
elif payment_type == "paypal":
    ...
elif payment_type == "crypto":
    ...
  • High Regression Testing Burden: Adding support for "Apple Pay" requires modifying a core class that has been running bug-free in production for two years, forcing a full QA regression test on Credit Card and PayPal.
  • Merge Conflicts Across Squads: Team A adding Crypto and Team B adding UPI both edit the same PaymentProcessor.process() method simultaneously.

the violation: branching payment processor

In this naive implementation, adding a new payment gateway forces us to open and edit the existing PaymentProcessor class:

● ● ●python — anti-pattern: branching payment processor
# ANTI-PATTERN: Violates Open/Closed Principle
class PaymentProcessor:
    def process_payment(self, payment_type: str, amount: float, **kwargs) -> bool:
        if payment_type == "credit_card":
            card_number = kwargs.get("card_number")
            cvv = kwargs.get("cvv")
            print(f"[CreditCard] Debiting ${amount} from card ending in {card_number[-4:]} with CVV {cvv}")
            return True
        elif payment_type == "paypal":
            email = kwargs.get("email")
            print(f"[PayPal] Debiting ${amount} from PayPal account {email}")
            return True
        elif payment_type == "crypto":
            wallet = kwargs.get("wallet_address")
            print(f"[Crypto] Transferring {amount} USD equivalent to wallet {wallet}")
            return True
        # Tomorrow: what happens when product managers ask for Apple Pay, UPI, Klarna, or Stripe?
        # You must EDIT this method, re-test credit card, and risk breaking production payments!
        else:
            raise ValueError(f"Unsupported payment type: {payment_type}")

the clean architecture refactor (strategy pattern)

We invert the design by establishing a stable contract (the socket) using Python's abc.ABC (or typing.Protocol) and implement concrete payment strategies (the plugs):

● ● ●python — clean architecture: strategy pattern with abstract base classes
# CLEAN ARCHITECTURE: Open for Extension, Closed for Modification
from abc import ABC, abstractmethod
from dataclasses import dataclass

# 1. The Stable Abstraction (Closed for Modification)
class PaymentStrategy(ABC):
    @abstractmethod
    def pay(self, amount: float) -> bool:
        """Process payment of amount. Returns True on success."""
        pass

# 2. Concrete Extensions (Open for Extension: add as many as you need!)
@dataclass
class CreditCardPayment(PaymentStrategy):
    card_number: str
    cvv: str
    expiry: str

    def pay(self, amount: float) -> bool:
        masked = self.card_number[-4:] if len(self.card_number) >= 4 else "****"
        print(f"[CreditCard] Successfully charged ${amount:.2f} to card ending in {masked}")
        return True

@dataclass
class PayPalPayment(PaymentStrategy):
    email: str

    def pay(self, amount: float) -> bool:
        print(f"[PayPal] Successfully charged ${amount:.2f} to account {self.email}")
        return True

@dataclass
class CryptoPayment(PaymentStrategy):
    wallet_address: str

    def pay(self, amount: float) -> bool:
        print(f"[Crypto] Successfully transferred ${amount:.2f} to wallet {self.wallet_address}")
        return True

# 3. New Requirement Added 6 Months Later: Apple Pay!
# Notice: ZERO lines of existing payment code are touched or re-tested.
@dataclass
class ApplePayPayment(PaymentStrategy):
    device_token: str

    def pay(self, amount: float) -> bool:
        print(f"[ApplePay] Authenticated via FaceID on token {self.device_token[:8]}... Paid ${amount:.2f}")
        return True

# 4. The High-Level Client
# Accepts ANY payment strategy complying with the contract.
class CheckoutService:
    def checkout(self, amount: float, strategy: PaymentStrategy) -> bool:
        print(f"[Checkout] Initiating checkout for order total: ${amount:.2f}")
        success = strategy.pay(amount)
        if success:
            print("[Checkout] Payment confirmed. Fulfilling order...")
        return success

dynamic runtime plugin registry

In high-scale systems, you often need to resolve strategies dynamically based on string inputs from an API request without introducing hardcoded if/elif trees. A Strategy Registry cleanly solves this:

● ● ●python — dynamic runtime strategy registry
class PaymentRegistry:
    def __init__(self):
        self._registry: dict[str, type[PaymentStrategy]] = {}

    def register(self, method_name: str, strategy_cls: type[PaymentStrategy]) -> None:
        """Register a new strategy plug-in at startup or runtime."""
        self._registry[method_name.lower()] = strategy_cls

    def create(self, method_name: str, **kwargs) -> PaymentStrategy:
        strategy_cls = self._registry.get(method_name.lower())
        if not strategy_cls:
            raise ValueError(f"Unknown payment method: {method_name}")
        return strategy_cls(**kwargs)

# Setup at application startup:
registry = PaymentRegistry()
registry.register("credit_card", CreditCardPayment)
registry.register("paypal", PayPalPayment)
registry.register("apple_pay", ApplePayPayment)

# Resolving dynamically from incoming HTTP payload:
strategy = registry.create("apple_pay", device_token="tok_apple_98314")
checkout = CheckoutService()
checkout.checkout(49.99, strategy)

when not to apply ocp (the yagni balance)

⚠️ beware of speculative generality
Do not invent interfaces and strategy patterns for things that are not expected to vary. If your system will only ever calculate sales tax with one standard state tax formula and will never support international jurisdictions, a simple function is superior to an abstract TaxCalculationStrategyFactoryProvider.

Rule of thumb: Follow the Rule of Three. Write simple code first. When the second or third variation arrives, refactor into an OCP-compliant abstraction.
⭐ interview gold standard
During LLD machine coding interviews (e.g. Discount Systems, Notification Engines, or Rate Limiters), interviewers will purposefully drop a curveball at minute 35:
"Great! Now suppose marketing wants a new discount rule: buy 2 get 1 free on footwear, but only on Tuesdays."
If your design requires editing existing discount logic, you fail the OCP test. If you simply create a new TuesdayFootwearBOGODiscount(DiscountPolicy) class and pass it in, the interviewer gives you top marks.
