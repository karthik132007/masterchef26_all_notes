subtypes must be substitutable for their base types without altering program correctness or breaking caller assumptions.

the core intuition

The Liskov Substitution Principle (LSP) was introduced by Turing Award winner Barbara Liskov in 1987. The formal mathematical definition states:

Let \(\phi(x)\) be a property provable about objects \(x\) of type \(T\). Then \(\phi(y)\) should be true for objects \(y\) of type \(S\) where \(S\) is a subtype of \(T\).

In everyday engineering terms:

"If code expects an instance of class A, passing an instance of subclass B must never break the correctness, invariants, or runtime behavior of the program."
🧷 the battery-operated duck mental model
If it looks like a duck and quacks like a duck, but requires batteries, you probably have the wrong abstraction. If your code expects a live duck, tosses it into a pond, and it sinks to the bottom because of battery weight, you have violated LSP. Subclasses must honor the behavioral expectations of the parent, not just match method signatures!

the 3 formal behavioral contract rules

LSP is governed by the Design by Contract paradigm (Bertrand Meyer). For a subclass to be truly substitutable, it must obey three strict contract conditions:

Contract RuleWhat It MeansViolation Example
1. Preconditions cannot be strengthened A subclass cannot demand stricter inputs or preconditions than the base class. Base accepts any positive integer; subclass throws an error if the integer is greater than 100.
2. Postconditions cannot be weakened A subclass must deliver at least the same guarantees/outcomes as the base class. Base guarantees writing to disk before returning; subclass leaves writes in an uncommitted buffer.
3. Invariants must be preserved A subclass must maintain all internal consistency rules guaranteed by the base class. Base guarantees width and height can vary independently; subclass forces them to stay equal.

code smells: how to spot lsp violations

  • Methods Throwing NotImplementedError: A subclass overrides a parent method solely to raise an error because it doesn't support that feature.
  • Empty Method Implementations (Stubs): Overriding a method with pass or a dummy return value because the subclass has no use for it.
  • Type-Checking (isinstance / instanceof): If calling code must check the runtime type before executing an action, the abstraction has failed:
    ● ● ●python — code smell: isinstance type-checking
    # SMELL: Indicates an LSP violation!
for account in accounts:
    if isinstance(account, FixedDepositAccount):
        # don't call withdraw!
    else:
        account.withdraw(500)

classic trap 1: the rectangle and square paradox

In Euclidean geometry, every square is a rectangle. But in object-oriented programming, a mutable Square is NOT a mutable Rectangle:

● ● ●python — anti-pattern: rectangle vs square paradox
# ANTI-PATTERN: Geometric intuition conflicts with OOP behavior
class Rectangle:
    def __init__(self, width: float, height: float):
        self._width = width
        self._height = height

    def set_width(self, width: float) -> None:
        self._width = width

    def set_height(self, height: float) -> None:
        self._height = height

    def area(self) -> float:
        return self._width * self._height


class Square(Rectangle):
    def __init__(self, size: float):
        super().__init__(size, size)

    # In a square, setting width must change height to maintain squareness!
    def set_width(self, width: float) -> None:
        self._width = width
        self._height = width

    def set_height(self, height: float) -> None:
        self._width = height
        self._height = height


# Caller function that relies on Rectangle's contract:
def resize_and_verify(rect: Rectangle) -> None:
    rect.set_width(5)
    rect.set_height(10)
    # The caller reasonably assumes: area == 5 * 10 == 50
    assert rect.area() == 50, f"Expected 50, but got {rect.area()}"

# Works fine with Rectangle:
resize_and_verify(Rectangle(2, 3))  # PASSES (area is 50)

# Catastrophically fails when substituted with Square!
# resize_and_verify(Square(2))      # AssertionError: Expected 50, but got 100!
⚠️ why did square break?
Rectangle has an invariant: changing width does not mutate height. Square silently mutates height when width changes. By breaking this invariant, Square cannot be safely substituted for Rectangle.

real-world trap 2: banking account hierarchies

In an enterprise banking system, a classic design mistake is forcing FixedDepositAccount (where funds are locked for 3 years) to inherit from a generic BankAccount that contains a withdraw() method:

● ● ●python — anti-pattern: broken contract with NotImplementedError
# ANTI-PATTERN: Subclass raises NotImplementedError
class BankAccount:
    def __init__(self, balance: float):
        self.balance = balance

    def deposit(self, amount: float) -> None:
        self.balance += amount

    def withdraw(self, amount: float) -> None:
        if amount > self.balance:
            raise ValueError("Insufficient balance")
        self.balance -= amount


class FixedDepositAccount(BankAccount):
    def withdraw(self, amount: float) -> None:
        # VIOLATION: Subtype weakens postconditions and breaks callers!
        raise NotImplementedError("Withdrawals are locked until maturity date!")

the clean architecture refactor (composition & role segregation)

To honor LSP, align classes around actual behavioral capabilities. Accounts that support withdrawal implement a withdrawable contract; locked accounts do not:

● ● ●python — clean architecture: capability segregation
# CLEAN ARCHITECTURE: Respects Liskov Substitution Principle
from abc import ABC, abstractmethod

# 1. Base abstraction representing accounts that hold a balance and accept deposits
class Account(ABC):
    def __init__(self, account_id: str, balance: float):
        self.account_id = account_id
        self._balance = balance

    @property
    def balance(self) -> float:
        return self._balance

    def deposit(self, amount: float) -> None:
        if amount <= 0:
            raise ValueError("Deposit amount must be strictly positive")
        self._balance += amount
        print(f"[Account {self.account_id}] Deposited ${amount:.2f}. New Balance: ${self._balance:.2f}")


# 2. Narrower capability interface for accounts that allow on-demand withdrawal
class Withdrawable(ABC):
    @abstractmethod
    def withdraw(self, amount: float) -> None:
        pass


# 3. Checking Account implements both capabilities
class CheckingAccount(Account, Withdrawable):
    def withdraw(self, amount: float) -> None:
        if amount <= 0:
            raise ValueError("Withdrawal must be positive")
        if amount > self._balance:
            raise ValueError("Insufficient funds")
        self._balance -= amount
        print(f"[Checking {self.account_id}] Withdrew ${amount:.2f}. Remaining: ${self._balance:.2f}")


# 4. Fixed Deposit Account only inherits Account capabilities
class FixedDepositAccount(Account):
    def __init__(self, account_id: str, balance: float, lock_period_months: int):
        super().__init__(account_id, balance)
        self.lock_period_months = lock_period_months


# 5. Client functions now depend only on the exact capability they require!
def process_monthly_interest(accounts: list[Account]) -> None:
    """Safe for ALL accounts — no exceptions possible!"""
    for acc in accounts:
        acc.deposit(10.0)

def process_batch_payout(accounts: list[Withdrawable], amount: float) -> None:
    """Type-safe by construction: impossible to pass a FixedDepositAccount here!"""
    for acc in accounts:
        acc.withdraw(amount)

the golden rule: composition over inheritance

🧷 prefer "has-a" over "is-a"
Most LSP violations stem from treating inheritance as a code-reuse mechanism rather than a strict behavioral subtype relationship. If two concepts share logic but not full behavioral substitutability, do not inherit. Instead, inject the shared behavior as a component via composition.
⭐ interview questions that test lsp
Interviewers love asking:
  1. "Can a ReadOnlyRepository inherit from a CrudRepository?"
    Answer: No! That violates LSP because save() and delete() would throw runtime exceptions. Split them into ReadableRepository and WritableRepository.
  2. "Why does Bird $\to$ FlyingBird $\to$ Penguin break LSP?"
    Answer: A Penguin is a Bird, but cannot fly. If Bird contains fly(), Penguin must either raise an error or no-op. Instead, make Flyable an independent capability interface.
