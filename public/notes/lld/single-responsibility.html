a module should be responsible to one, and only one, actor — isolating the blast radius of business changes.

the core intuition

The Single Responsibility Principle (SRP) is the most frequently quoted — and most frequently misunderstood — principle in software engineering. Many developers define it as: "A class should do only one thing." That is incorrect; functions do one thing, but classes naturally orchestrate multiple cooperating operations.

The definitive formulation by Robert C. Martin is:

"A class should have one, and only one, reason to change."

And more precisely:

"A module should be responsible to one, and only one, actor."
🧷 who is the actor?
An actor is a stakeholder, department, or business role that requests changes to the system:
  • The CFO / Accounting cares about tax calculations, currency conversions, and ledger audits.
  • The COO / Operations cares about fulfillment status, inventory tracking, and warehouse routing.
  • The CTO / DBA cares about database schemas, connection pooling, and JSON persistence.
If a single class serves requirements for both the CFO and the DBA, you have violated SRP. When the DBA migrates from PostgreSQL to DynamoDB, they should never risk breaking the CFO's tax computation!

code smells: how to spot srp violations

  • The God Object (The Blob): A monster class with 2,000+ lines containing business logic, SQL queries, HTTP client calls, and HTML/PDF rendering.
  • Divergent Change: You find yourself opening the same file when fixing a database bug, when redesigning an email template, and when adjusting pricing logic.
  • Constant Git Merge Conflicts: Multiple developers working on completely unrelated features (billing vs notifications) keep getting merge conflicts on the exact same class.
  • Fragile Unit Tests: Testing a simple discount calculation requires mocking an entire database connection pool and an SMTP mail server.

the violation: the monolithic order manager

Consider an e-commerce order class that violates SRP by taking on domain math, persistence, PDF formatting, and email delivery:

● ● ●python — anti-pattern: monolithic order manager
# ANTI-PATTERN: Violates Single Responsibility Principle
import sqlite3
import smtplib
from email.mime.text import MIMEText

class Order:
    def __init__(self, order_id: str, customer_email: str, items: list[dict]):
        self.order_id = order_id
        self.customer_email = customer_email
        self.items = items
        self.total_amount = 0.0

    # Actor 1: Finance / Business Logic
    def calculate_total(self, tax_rate: float, discount_code: str = "") -> float:
        subtotal = sum(item["price"] * item["quantity"] for item in self.items)
        discount = 0.10 if discount_code == "SUMMER10" else 0.0
        self.total_amount = subtotal * (1 - discount) * (1 + tax_rate)
        return self.total_amount

    # Actor 2: DBA / Infrastructure
    def save_to_database(self) -> None:
        conn = sqlite3.connect("ecommerce.db")
        cursor = conn.cursor()
        cursor.execute(
            "INSERT INTO orders (id, email, total) VALUES (?, ?, ?)",
            (self.order_id, self.customer_email, self.total_amount)
        )
        conn.commit()
        conn.close()

    # Actor 3: Marketing / Customer Support
    def send_confirmation_email(self) -> None:
        msg = MIMEText(f"Thank you for order {self.order_id}! Total: ${self.total_amount:.2f}")
        msg["Subject"] = "Order Confirmation"
        msg["From"] = "orders@shop.com"
        msg["To"] = self.customer_email

        with smtplib.SMTP("smtp.shop.com", 587) as server:
            server.login("user", "password")
            server.send_message(msg)
⚠️ why this breaks in production
If the security team requires updating the SMTP authentication protocol, you have to modify and re-deploy Order. A typo introduced during the email change can silently corrupt the financial calculate_total method. Furthermore, writing a unit test for calculate_total requires fake DB credentials and dummy SMTP servers!

the clean architecture refactor

We decompose the monolithic class into cohesive, focused modules. Each class serves exactly one actor and has one reason to change:

● ● ●python — clean architecture: cohesive domain services
# CLEAN ARCHITECTURE: Respects Single Responsibility Principle
from dataclasses import dataclass
from typing import Protocol

# 1. Pure Domain Model (The Data Entity)
# Responsible only for representing order state.
@dataclass(frozen=True)
class OrderItem:
    sku: str
    price: float
    quantity: int

@dataclass
class Order:
    order_id: str
    customer_email: str
    items: list[OrderItem]

# 2. Financial Pricing Engine (Actor: CFO / Accounting)
# Responsible only for pricing rules and discount policies.
class OrderPricingEngine:
    @staticmethod
    def calculate_total(order: Order, tax_rate: float, discount_percent: float = 0.0) -> float:
        subtotal = sum(item.price * item.quantity for item in order.items)
        discounted = subtotal * (1.0 - (discount_percent / 100.0))
        return round(discounted * (1.0 + tax_rate), 2)

# 3. Persistence Boundary (Actor: DBA / System Architecture)
# Abstract repository interface decoupling domain from SQL.
class OrderRepository(Protocol):
    def save(self, order: Order, total_amount: float) -> None:
        ...

class SqliteOrderRepository:
    def __init__(self, db_path: str):
        self.db_path = db_path

    def save(self, order: Order, total_amount: float) -> None:
        # DB connection and SQL logic isolated here
        print(f"[DB] Stored order {order.order_id} with total {total_amount} into {self.db_path}")

# 4. Notification Gateway (Actor: Marketing / Communications)
class NotificationService(Protocol):
    def send_order_receipt(self, email: str, order_id: str, total_amount: float) -> None:
        ...

class EmailNotificationService:
    def __init__(self, smtp_host: str):
        self.smtp_host = smtp_host

    def send_order_receipt(self, email: str, order_id: str, total_amount: float) -> None:
        print(f"[Email] Dispatched receipt for {order_id} (${total_amount}) to {email} via {self.smtp_host}")

# 5. Application Orchestrator (Coordinates the domain workflow)
class OrderCheckoutUseCase:
    def __init__(
        self,
        pricing: OrderPricingEngine,
        repository: OrderRepository,
        notifier: NotificationService
    ):
        self.pricing = pricing
        self.repository = repository
        self.notifier = notifier

    def checkout(self, order: Order, tax_rate: float, discount_percent: float = 0.0) -> float:
        total = self.pricing.calculate_total(order, tax_rate, discount_percent)
        self.repository.save(order, total)
        self.notifier.send_order_receipt(order.customer_email, order.order_id, total)
        return total

the mechanical architectural payoff

Quality AttributeBefore Refactoring (Monolith)After Refactoring (SRP Applied)
Unit TestabilityNightmare. Requires mock DB sockets and SMTP servers just to test an arithmetic tax formula.Trivial. OrderPricingEngine is a pure function tested with standard inputs and zero mocks.
Change IsolationSwitching from SQLite to PostgreSQL risks breaking order calculation and notification dispatch.Zero risk. Only OrderRepository changes; pricing and email systems are untouched.
Team ScalabilityMerge conflicts when billing and communication teams touch Order concurrently.Billing devs own OrderPricingEngine; infra devs own OrderRepository.
⭐ machine coding interview tip
When an interviewer asks you to design a system (e.g. Splitwise, Parking Lot, or an ATM), do not dump everything into a ParkingLot or Bill class. Separate:
  1. Entities / State: The immutable data representations (e.g. ParkingTicket, Spot).
  2. Policy / Strategy: The business math (e.g. HourlyFeeCalculator, PeakRateCalculator).
  3. Storage / Registry: Tracking active spots and tickets (e.g. SpotAllocationRepository).
