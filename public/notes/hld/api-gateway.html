the single front door: edge authentication, token buckets, and shielding your backend from the chaos of the internet.

the 30-second elevator pitch

An API Gateway is the unified single ingress entry point that sits between external clients (mobile apps, web browsers, public API consumers) and your internal microservices fleet.

  • The Client Decoupler: External clients talk to one domain (api.example.com). They never know whether you run a monolith, 50 microservices in Go, or a legacy mainframe.
  • Cross-Cutting Edge Guard: It centralizes non-business logic at the perimeter: Authentication, SSL Termination, Rate Limiting, Request Aggregation (BFF), and Load Shedding.
  • The Golden Architectural Rule: Keep it thin. Never leak business domain rules into gateway filter scripts. The moment your gateway starts reading product catalogs from a database, you’ve built a catastrophic bottleneck.

why microservices need an api gateway

Without an API Gateway, client applications would have to talk directly to dozens of individual microservices. In production, this causes four major architectural failures:

1. Massive Attack Surface

Every internal microservice would need a public IP address, open internet firewall ports, and independent DDoS defense. With a Gateway, only one IP is public; all microservices live hidden inside a private VPC.

2. Cellular Radio Latency

Mobile devices on cellular radios cannot afford 10 sequential HTTP requests to render one screen. The Gateway aggregates internal calls concurrently and returns one compressed payload.

3. Leaky Internal Topology

If you split or rename a backend service, you break every client in production. The Gateway acts as a stable contract façade — backend services can be rewritten or split without changing public API URLs.

4. Duplicated Security Logic

Without a gateway, every team independently writes JWT parsing, CORS handling, and rate limiting. The Gateway centralizes these cross-cutting concerns at the perimeter.

edge authentication: the stateless jwt pattern

The Disaster Pattern: Every microservice independently calls the Auth Service over the network to check whether a session is valid. 100k requests/sec creates 100k internal network calls to an Auth database that promptly catches fire.

The Staff Solution: Validate at the Edge using Asymmetric JWTs (JSON Web Tokens):

  1. The Auth service signs the token with its Private Key upon login.
  2. The API Gateway downloads the Auth service’s public keys (JWKS endpoint) once and caches them in memory.
  3. When a request arrives with Authorization: Bearer <token>, the gateway verifies the cryptographic signature locally in microsecond math (zero database lookups!).
  4. The gateway strips the heavy raw token and injects clean, trusted plaintext headers for downstream services: 
    X-User-Id: 98124
X-User-Role: admin
X-User-Tenant: enterprise_acme
  5. Because internal services live inside an isolated VPC, they trust these headers implicitly.

rate limiting algorithms: token bucket vs leaky bucket

Rate limiting protects your systems from DDoS attacks, rogue scripts, and noisy neighbors. There are four core algorithms tested in system design interviews:

AlgorithmMechanismHandles Bursts?Trade-Off
Token Bucket (Standard) Tokens fill a bucket at a fixed rate. Each request consumes 1 token. When empty, requests are rejected. Yes (up to bucket capacity) Most common (AWS, Stripe, GitHub). Allows legitimate bursts of traffic without dropping packets.
Leaky Bucket Requests enter a queue (bucket) and leak out to workers at a strict, continuous constant rate. No (smooths traffic flat) Great for traffic shaping when downstream databases cannot handle any spikes, but adds latency to bursts.
Fixed Window Counter Count requests in 1-minute blocks (e.g. 10:00:00 to 10:01:00). Reset to zero at the minute mark. Flawed at edges A user can send the entire limit at 10:00:59 and another full limit at 10:01:01 (2x burst across window!).
Sliding Window Log Keep timestamps of every request in a Redis Sorted Set (ZSET). Drop timestamps older than 60s. Accurate Memory heavy for high-volume users because every request timestamp is saved in RAM.

the bff pattern: backend-for-frontend

Modern apps don't have just one client. They have iOS apps on weak mobile cellular data, web dashboards on high-speed fiber, and third-party API partners.

  • The Problem: A web page needs 50 fields. A mobile smartwatch only needs 3 fields. Making the mobile app download the 50-field payload wastes cellular bandwidth and battery.
  • The BFF Solution: Deploy separate lightweight gateway layers: Mobile BFF and Web BFF.
    • Mobile BFF calls internal microservices in parallel, strips unused JSON keys, and returns a lean 2KB payload.
    • Web BFF returns rich payloads and pre-computed charts.

preventing the single point of failure (spof)

If all traffic flows through the API Gateway, doesn't that make it a dangerous Single Point of Failure?

In production cloud architecture, an API Gateway is stateless. Here is how FAANG makes it survive data center failures:

  1. GeoDNS Anycast: Client DNS queries resolve to the closest edge point of presence (PoP).
  2. Layer 4 ECMP (Equal-Cost Multi-Path) Routers: Hardware routers balance raw TCP packets across a fleet of stateless gateway instances without terminating connections.
  3. Auto-scaling Fleet: Gateway instances scale automatically based on CPU and network I/O. If two gateway nodes crash, ECMP immediately distributes packets across the surviving nodes in zero milliseconds.

faang interview defense & war stories

Interview QuestionKey Architectural InsightThe Winning Answer
"How do you implement distributed rate limiting without Redis becoming a bottleneck?" Local caching + batch synchronization Don't make an atomic Redis call on every single HTTP request. Allocate token blocks locally to each gateway pod (e.g. 50 tokens at a time). Pods consume from their local memory cache and sync back to Redis asynchronously every 100ms.
"What is Load Shedding and how does it differ from Rate Limiting?" Rate limiting checks user identity; load shedding checks server survival. Rate limiting protects against individual abusive users. Load shedding activates when internal CPU or queue latency exceeds safety limits (e.g. 85% CPU). The gateway drops non-critical requests (analytics, recommendations) returning 503 so checkout and payment traffic survive.
"What is 'The Fat Gateway' anti-pattern?" Leaking domain logic into infrastructure. Developers start writing business validation, database queries, and transformation code inside Lua or JavaScript gateway filters. Soon, the gateway becomes an unmaintainable monolithic bottleneck that is impossible to test and redeploy safely.

the 20-second summary

An API Gateway is your system’s single ingress security guard. It terminates TLS, validates stateless JWTs against cached JWKS keys, enforces Token Bucket rate limits, and aggregates microservices using the BFF pattern. Keep it thin, stateless, and scale it behind Layer 4 ECMP routers to eliminate Single Points of Failure.
