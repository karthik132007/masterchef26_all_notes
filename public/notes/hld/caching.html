sub-millisecond reads from ram, cache invalidation math, and surviving the big three production disasters.

the 30-second elevator pitch

"There are only two hard things in Computer Science: cache invalidation and naming things." — Phil Karlton.

A cache is a high-speed, volatile storage layer (almost always RAM) that holds copies of data so future read requests are served in sub-milliseconds rather than hitting slow disks, complex SQL joins, or external APIs.

  • The Speed Multiplier: Reading from RAM takes ~100 nanoseconds. Reading from an NVMe SSD takes ~50 microseconds (500x slower). Reading from a spinning hard disk takes ~10 milliseconds (100,000x slower).
  • The Golden Formula: Average Latency = $(H \times \text{Cache Latency}) + ((1 - H) \times \text{DB Latency})$, where $H$ is the Cache Hit Ratio. A 98% hit ratio drops average query latency from 25ms down to 0.9ms!
  • The Cardinal Rule: Cache is temporary. If your cache cluster burns down, your primary database must still be able to reconstruct the truth without permanent data loss.

multi-tier caching architecture

In production, you never have just "one cache." You have a multi-layered defensive hierarchy:

  1. Browser / Client Cache: Assets and HTTP API responses cached via headers (Cache-Control: public, max-age=3600, ETag, 304 Not Modified). Zero network calls leave the device.
  2. CDN / Edge Cache (Cloudflare, CloudFront): Geographically distributed PoPs caching static images, videos, and dynamic edge-rendered HTML within 15ms of the user.
  3. Reverse Proxy Cache (Nginx): Micro-caching popular anonymous public endpoints for 1-2 seconds. Absorbs sudden viral traffic spikes.
  4. Application L1 In-Memory Cache (Caffeine / Guava): Stored directly inside the application's JVM/Go process heap. ~10 nanoseconds access. Zero network serialization overhead.
  5. Distributed L2 Cache (Redis Cluster): Shared memory layer across all 200 application pods. Highly available, partitioned via consistent hashing, persistence via RDB/AOF.

cache write strategies: the 4 core patterns

Every system design interview requires picking a caching strategy. Choosing the wrong one causes silent data corruption or DB meltdowns:

1. Cache-Aside (Lazy Loading)

The Industry Standard. Application code coordinates both cache and DB.

  • Read: Check Cache. If Hit $\to$ return. If Miss $\to$ read DB, write result to Cache, return.
  • Write: Update DB, then evict (delete) the key from Cache.
  • Why evict instead of update? Prevents race conditions where two concurrent writes overwrite cache in reverse order!

2. Write-Through

Application writes strictly to the cache. The cache synchronously writes to the database before returning success.

  • Pros: Data in cache is never stale; immediate read consistency.
  • Cons: High write latency (waits for both cache and DB writes to complete).

3. Write-Back (Write-Behind)

Application writes to cache; cache acknowledges immediately in 0.5ms. The cache batches dirty writes and flushes them to the database asynchronously.

  • Pros: Blazing write speeds. Ideal for write-heavy counters, gaming leaderboards, and telemetry.
  • Cons: High risk! If the Redis node crashes before flushing to disk, recent writes are permanently lost.

4. Write-Around

Writes bypass the cache completely and write directly to the database. Cache is only populated on subsequent read misses.

  • Best for: Data that is written once and rarely read again (e.g. archived audit logs, legal compliance records). Prevents cache pollution.

cache eviction: how memory is reclaimed

Caches have finite RAM. When memory is full, an eviction policy decides who gets thrown out:

  • LRU (Least Recently Used): Evicts the item that hasn't been accessed for the longest time. Implemented via a Doubly-Linked List + Hash Map for $O(1)$ lookup and $O(1)$ head re-ordering.
  • LFU (Least Frequently Used): Evicts the item with the lowest historical access frequency. Great when certain items are evergreen hits, but slow to adapt to sudden new trending items.
  • TTL (Time-To-Live): Explicit expiration time (e.g. 15 minutes). Essential to prevent stale ghost data from lingering forever.

the big 3 cache disasters & production defenses

This is the most heavily tested topic in senior system design interviews. Every candidate must know these three catastrophic failure modes and their exact engineering solutions:

DisasterWhat HappensHow to Defend (Interview Answer)
1. Cache Penetration Malicious or rogue traffic requests keys that do not exist in the DB (e.g. user_id = -99999). The cache misses every time, forwarding 100% of queries directly to the DB, causing database CPU starvation. 1. Bloom Filter: Place a space-efficient Bloom Filter in front of the cache. If the filter says the key does not exist, reject it immediately ($O(1)$ bit check).
2. Cache Null Objects: On a DB miss, store key $\to$ null in Redis with a short TTL (e.g. 30 seconds).
2. Cache Avalanche Thousands of cache keys are loaded at midnight with the exact same 24-hour TTL. At 00:00:00 tomorrow, all 100,000 keys expire simultaneously. Traffic surges directly into the database, causing immediate collapse. 1. TTL Jitter: Never use fixed expiration. Add random jitter: TTL = base_ttl + rand(0, 300) seconds so keys expire gradually over time.
2. Redis High Availability: Multi-AZ master-replica clusters with Redis Sentinel or AWS ElastiCache auto-failover.
3. Cache Stampede (Thundering Herd) A single super-hot key (e.g. World Cup final score, viral tweet) expires. 50,000 concurrent requests miss the cache at the exact same millisecond. All 50,000 threads execute the expensive SQL query simultaneously. 1. Distributed Mutex (Redlock): Use Redis SETNX (Set if Not Exists) lock. Only the 1 thread that acquires the lock queries the DB; the other 49,999 wait or return the stale cache value.
2. Probabilistic Early Expiration (XFetch): Background threads recompute the value before it actually expires based on request frequency.

"How do you handle the celebrity / hot-key problem in Redis (e.g. Cristiano Ronaldo has 600M followers)?" Sharding hot keys & local L1 caching A single Redis shard can saturate its 100k ops/sec limit on a single key. Two defenses: 1) Key Salting: Replicate the key across $N$ shards as user:ronaldo:1, user:ronaldo:2 and randomly query one. 2) L1 Near-Cache: Cache the celebrity profile directly in the JVM/Go heap (Caffeine) for 5 seconds.
"Why is deleting a cache key safer than updating it on DB writes?" Race condition prevention If Client A updates DB to $V_1$, then Client B updates DB to $V_2$. If network latency causes Client B to write cache first and Client A second, the cache permanently holds stale $V_1$ while DB holds $V_2$. Deleting the key forces the next read to fetch the true DB value.

the 20-second summary

Caching leverages RAM to drop latency from 25ms to sub-milliseconds. Use Cache-Aside with eviction on write to prevent race conditions. Protect your systems against Penetration (Bloom Filters), Avalanche (TTL Jitter), and Stampede (Distributed Mutex). Pick Redis for rich data structures and clustering, and Memcached for simple multi-threaded key-value scaling.
