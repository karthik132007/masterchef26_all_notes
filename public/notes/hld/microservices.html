independent deployments, bounded contexts, database-per-service — and the distributed systems tax.

the 30-second elevator pitch

A microservices architecture decomposes an application into small, autonomous services modeled around business domains (Domain-Driven Design). Each service runs in its own process, deploys independently, and strictly owns its private datastore.

  • The Golden Rule: Database-Per-Service. Service A never queries Service B's database directly. Communication occurs strictly over network protocols (REST, gRPC, or messaging queues).
  • The Core Benefit: Independent scaling and deployment velocity. The Payments team can ship 15 times a day using Go and PostgreSQL without coordinating with the Catalog team using Python and MongoDB.
  • The Distributed Systems Tax: You trade monolithic simplicity for network latency, partial failures, distributed transaction complexity, dual-write bugs, and operational overhead.
⭐ the #1 interview red flag
If an interviewer asks: "Can two microservices connect to the same PostgreSQL instance on different tables?" The answer is NO. Shared databases create hidden schema coupling, bypass domain validation logic, and create a single point of failure (SPOF) that defeats the purpose of microservices.

inter-service communication: sync vs async

Microservices talk to each other through two distinct paradigms: synchronous remote calls and asynchronous event streams.

ProtocolTypeLatencyBest Used ForFailure Mode
REST (HTTP/1.1 JSON) Synchronous 5 - 20 ms Public client-to-backend APIs, simple CRUD queries Cascading timeouts when downstream services stall
gRPC (HTTP/2 Protobuf) Synchronous 1 - 3 ms High-throughput internal service-to-service RPC Binary serialization requires shared contract (.proto)
Kafka Asynchronous (Event Log) Sub-millisecond (Enqueue) High-volume event streams (100k+ msg/s), state replication, auditable event sourcing Consumer lag, partition rebalancing, eventual consistency
RabbitMQ Asynchronous (Message Queue) Sub-millisecond (Enqueue) Complex task routing, job workers, point-to-point guaranteed command delivery Memory bottlenecks if queues back up under high load

the distributed transactions nightmare: 2pc vs sagas

In a monolith, transferring money or placing an order is an atomic ACID database transaction. In microservices, placing an order requires mutating three independent databases: Orders DB, Payments DB, and Inventory DB.

Why Two-Phase Commit (2PC) Fails in the Cloud

2PC relies on a central coordinator asking all services: "Can you commit?" (Phase 1: Prepare), followed by "Commit now" (Phase 2: Commit). In cloud environments, 2PC is an anti-pattern because:

  • It holds database locks across network boundaries. If one node experiences a 500ms network blip, all participating rows stay locked.
  • If the coordinator crashes between phases, the entire cluster hangs indefinitely in a half-committed state.

The Industry Solution: The Saga Pattern

A Saga is a sequence of local transactions. Each transaction updates data in a single service and publishes an event. If a subsequent step fails, the Saga executes compensating transactions to undo the previous steps.

1. Choreography-Based Saga

Services listen to events and trigger their own next step without a central coordinator. OrderCreated → Payment listens and charges card → PaymentProcessed → Inventory listens and reserves stock.

Pros: Simple for 2-3 services.
Cons: Spaghettifies quickly; impossible to visualize the complete flow when you have 10+ services.

2. Orchestration-Based Saga

A dedicated central orchestrator (e.g., Temporal, AWS Step Functions, or Camunda) manages the state machine. It explicitly tells Order Svc → Payment Svc → Inventory Svc what to do.

Pros: Clear state visibility, automatic retry logic, clean compensating rollbacks.
Cons: Single point of orchestration management.

⚠️ compensating actions are not rollbacks
In a database rollback, nobody ever saw the intermediate state. In a Saga, the customer's card was actually charged! The compensating transaction is a refund, not a rewind. Your business logic must handle partial visibility (e.g., displaying order status as PENDING_PAYMENT).

the dual-write problem & transactional outbox

A classic production bug: your service updates its local database, then publishes an event to Kafka:

# The Naive Approach (BROKEN IN PRODUCTION)
db.orders.insert(order)          # 1. DB write succeeds
kafka.publish("OrderCreated")     # 2. Network timeout! Event lost forever!

If you swap the order (publish to Kafka first, then insert DB), the DB write might throw a constraint violation, sending a phantom event downstream!

The Fix: The Transactional Outbox Pattern

Instead of talking directly to Kafka, write the event into an outbox table inside the exact same local ACID transaction as the business data:

BEGIN TRANSACTION;
  INSERT INTO orders (id, user_id, amount) VALUES (101, 'alice', 50.00);
  INSERT INTO outbox (event_type, payload) VALUES ('OrderCreated', '{"id":101}');
COMMIT;

An asynchronous background reader (like Debezium using PostgreSQL Change Data Capture / WAL) streams rows from outbox to Kafka with zero dual-write anomalies!

resilience engineering: circuit breakers

In distributed systems, failures are guaranteed. If Service C begins timing out, Service B keeps sending requests, saturating its thread pool. In seconds, Service A runs out of memory, and your entire architecture experiences a cascading collapse.

The Circuit Breaker Pattern wraps downstream calls with a 3-state protective breaker:

  • CLOSED (Normal): All requests pass through. The breaker tracks the percentage of failed requests in a sliding window (e.g. last 100 requests).
  • OPEN (Tripped): If error rate exceeds the threshold (e.g. 50%), the circuit trips OPEN. All calls fail immediately without touching the downstream service, returning cached or fallback responses!
  • HALF-OPEN (Testing): After a cooldown period (e.g. 15 seconds), the circuit lets a limited number of test requests through. If they succeed, it transitions back to CLOSED. If they fail, it snaps back to OPEN.

distributed tracing: following the breadcrumbs

When an error occurs across 15 hops, standard log files are useless. You need Distributed Tracing (W3C Trace Context standard):

  • Trace ID: A globally unique ID assigned at the API Gateway to represent the entire end-to-end user request. It is propagated across HTTP headers via traceparent: 
    traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01
  • Span ID: Identifies work done by a single specific service or database call within that trace.
  • OpenTelemetry (OTel): The vendor-neutral industry standard SDK used to collect and export traces to Jaeger, Zipkin, or Datadog.

faang interview defense & war stories

Interview QuestionKey Architectural InsightThe Winning Answer
"How do you handle data consistency without 2PC?" Sagas, Eventual Consistency, and Idempotency Use an orchestration or choreography Saga pattern with compensating transactions. Design all downstream event handlers to be strictly idempotent using idempotency keys, and store events in a Transactional Outbox.
"Why did Amazon Prime Video move back to a monolith?" Avoiding microservices over-engineering Prime Video originally used AWS Step Functions and Lambda microservices to process video streams frame by frame. Orchestrating millions of tiny calls over S3 and SQS hit account rate limits and cost a fortune. Consolidating into a single monolithic process running in ECS reduced infrastructure costs by 90%.
"How do you query across two separate microservice databases?" CQRS and read projections Never do cross-database joins over HTTP. Use Command Query Responsibility Segregation (CQRS). Both services stream updates to Kafka, which feeds a materialized read-model (e.g. Elasticsearch or read-only Postgres) optimized for complex joins.

the 20-second summary

Microservices divide systems by business domains with strict database-per-service boundaries. Connect them with gRPC for low-latency sync calls and Kafka for decoupled async events. Guarantee data integrity using the Saga pattern and Transactional Outbox, and prevent cascading system-wide collapses using Circuit Breakers with fast fallbacks.
