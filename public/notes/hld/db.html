data has gravity: storage engine internals, replication lag traps, and partitioning without cross-shard pain.

the 30-second elevator pitch

Application compute is stateless and easy to scale — spin up 20 more Docker containers behind a load balancer and you’re done. Databases are stateful and hard. Data has physics, gravity, and disk constraints.

  • The Fundamental Trade-Off: Every database engine optimizes for either fast reads (B+ Trees, normalized SQL) or fast writes (LSM-Trees, append-only logs). No single database excels at both simultaneously.
  • Replication vs Sharding: Replication copies the exact same data to multiple servers to scale read throughput and provide fault tolerance. Sharding splits different rows across different servers to scale storage capacity and write throughput.
  • The Golden Rule of System Design: Scale vertically first (beefier instance + connection pooling). Add read replicas second. Cache in Redis third. Only shard when you have exhausted all single-node options.

under the hood: b+ trees vs lsm-trees

Why is PostgreSQL read-optimized while Cassandra is write-optimized? It comes down to their internal storage engine architecture:

1. B+ Tree (Postgres, MySQL InnoDB)

Data is stored in balanced, page-sized disk blocks (usually 8KB to 16KB). Every leaf node is linked to its neighbor in a double-linked chain.

  • Read Speed: $O(\log N)$ disk seeks. Range scans (BETWEEN 10 AND 50) are blazing fast because leaves are sequentially chained.
  • Write Bottleneck: Updating a single row requires reading a full 16KB page, modifying it in RAM, and writing it back to a random disk location (**Write Amplification**).

2. LSM-Tree (Cassandra, RocksDB, ScyllaDB)

Log-Structured Merge-Tree. Disks hate random writes, but love sequential append writes. LSM-Trees exploit this physical property.

  • Write Speed: Every write appends sequentially to an in-memory MemTable (SkipList) and a disk-based Write-Ahead Log (WAL). Zero random disk seeks! $O(1)$ write speed.
  • SSTables & Compaction: When MemTable fills, it flushes to disk as an immutable Sorted String Table (SSTable). Background threads continuously merge-sort SSTables.
  • Read Defense: Uses Bloom Filters to instantly skip SSTables that don’t contain the requested key.

scaling databases 1: replication & the replication lag trap

To scale reads, deploy a Primary-Replica (Master-Slave) topology: all writes go to the Primary, which asynchronously streams its write-ahead log (WAL) to $N$ Read Replicas.

⚠️ the replication lag disaster
A user updates their profile name from "Alice" to "Alice Smith" (written to Primary). The frontend immediately redirects and fetches the profile (routed to a lagging Read Replica). The replica hasn't received the WAL change yet! The user sees "Alice" and angrily submits the form a second time.

The Staff Solution (Read-Your-Own-Writes Consistency):
  • For 5 seconds after a user performs a write, route that specific user’s read queries strictly to the Primary DB.
  • Track the transaction Log Sequence Number (LSN). Replicas block read queries until their local LSN matches or exceeds the user's write LSN.

scaling databases 2: horizontal sharding

When write volume or dataset size exceeds what the biggest AWS RDS instance can hold, you must shard: partitioning rows across independent physical database servers.

Choosing the Right Shard Key

  • Bad Shard Key: Timestamp (created_at): Today's writes all hit Shard 4 (**hotspotting**), while Shards 1, 2, and 3 sit completely idle.
  • Bad Shard Key: Country / Geo: 70% of your users live in the US $\to$ US shard melts while the NZ shard is at 1% CPU.
  • Good Shard Key: High Cardinality + Even Distribution (user_id or hash(tenant_id, entity_id)): Spreads write traffic uniformly across all available hardware nodes.

The 3 Sharding Nightmares

  1. Cross-Shard Joins: SQL JOIN between tables living on different physical machines is impossible. You must fetch data in the application layer and join in memory, or denormalize data.
  2. Cross-Shard Transactions: If an atomic operation spans Shard A and Shard B, you need distributed Sagas or 2PC.
  3. Resharding: When Shard 2 fills up to 95% capacity, splitting it and moving 50% of its data to a new Shard 5 without downtime is a massive, high-risk engineering project.

the theoretical pillars: cap vs pacelc

1. The CAP Theorem

In any distributed data store, when a Network Partition (P) occurs, you can only choose one:

  • CP (Consistency): Reject reads/writes if nodes cannot synchronize. Guarantee zero stale reads (e.g. HBase, CockroachDB, etcd).
  • AP (Availability): Accept all reads and writes; allow temporary divergence and reconcile later (e.g. Cassandra, DynamoDB).
  • Why CA is a Myth: Networks in the real world physically disconnect (cable cuts, switch failures). You cannot choose "No Partition".

2. The PACELC Theorem

CAP only describes systems when there is a partition. PACELC describes normal operations too:

If Partition (P): Choose Availability (A) or Consistency (C);
Else (E): Choose Latency (L) or Consistency (C).

  • PA/EL (e.g. Cassandra): Under partition, remain available. In normal state, prioritize sub-millisecond latency over strong consistency.
  • PC/EC (e.g. PostgreSQL sync replica): Always prioritize strict consistency over latency and availability.

the 20-second summary

Storage engines dictate performance: B+ Trees excel at fast reads and range queries, while LSM-Trees maximize write throughput via sequential disk appends. Scale reads with Primary-Replica replication (defending against replication lag via Read-Your-Own-Writes). Scale writes with Horizontal Sharding using Consistent Hashing, and embrace PACELC to balance latency against consistency.
