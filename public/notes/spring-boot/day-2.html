JDBC makes the mapping visible; ORM makes the mapping reusable.

today's outcome

You will be able to explain the exact chain JDBC → ORM → JPA → Hibernate, map Java classes to tables, describe basic relationships, and build a runnable Maven JPA project with entities, configuration, and transactions.

the five words students mix up

TermSimple meaning
JDBCJava's low-level API for sending SQL to a database.
ORMA technique for mapping relational rows and tables to objects and classes.
JPAA standard API/specification describing persistence annotations and operations.
HibernateA popular ORM framework that implements JPA.
Spring Data JPAA Spring abstraction that creates repository implementations on top of JPA.
⭐ exam answer
JPA is not Hibernate. JPA defines the contract; Hibernate is one implementation of that contract.

4. set up the entity class

Save this as src/main/java/com/example/jpa/Student.java. Each public class belongs in its own matching file, and the package must match the name registered in persistence.xml.

package com.example.jpa;

import jakarta.persistence.Column;
import jakarta.persistence.Entity;
import jakarta.persistence.GeneratedValue;
import jakarta.persistence.GenerationType;
import jakarta.persistence.Id;
import jakarta.persistence.Table;

@Entity
@Table(name = "students")
public class Student {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(nullable = false)
    private String name;

    @Column(nullable = false, unique = true)
    private String email;

    protected Student() {
        // Required by JPA to create entity instances.
    }

    public Student(String name, String email) {
        this.name = name;
        this.email = email;
    }

    public Long getId() { return id; }
    public String getName() { return name; }
    public String getEmail() { return email; }
    public void setName(String name) { this.name = name; }
    public void setEmail(String email) { this.email = email; }
}
  • @Entity maps a class to persistent data; @Table sets the table name.
  • @Id is mandatory. IDENTITY lets the database generate the identifier; leave it unset for new students.
  • @Column adds database constraints. The unique email constraint is useful for the rollback exercise.
  • JPA requires a public or protected no-argument constructor. Keep the entity class non-final.
  • Putting @Id on a field selects field access: JPA can read and write private fields. Getters and setters are for application code; an ID setter is unnecessary here.

5. bootstrap JPA and run transactions

Save this as src/main/java/com/example/jpa/App.java. It creates, reads, updates, and deletes one student. Each write uses begin() and commit(). This introductory example follows the successful execution path; error handling is omitted.

package com.example.jpa;

import jakarta.persistence.EntityManager;
import jakarta.persistence.EntityManagerFactory;
import jakarta.persistence.EntityTransaction;
import jakarta.persistence.Persistence;

public class App {
    public static void main(String[] args) {
        EntityManagerFactory factory =
                Persistence.createEntityManagerFactory("studentPU");
        EntityManager em = factory.createEntityManager();
        EntityTransaction tx = em.getTransaction();

        // Create
        tx.begin();
        Student student = new Student("Asha", "asha@example.com");
        em.persist(student);
        tx.commit();
        Long studentId = student.getId();
        System.out.println("Created student id: " + studentId);

        // Read from the database instead of the first-level cache.
        em.clear();
        Student saved = em.find(Student.class, studentId);
        System.out.println("Read: " + saved.getName());

        // Update the managed entity.
        tx.begin();
        saved.setName("Asha Rao");
        tx.commit();
        em.clear();
        Student updated = em.find(Student.class, studentId);
        System.out.println("Updated: " + updated.getName());

        // Delete
        tx.begin();
        em.remove(updated);
        tx.commit();
        em.clear();
        System.out.println("Deleted: " +
                (em.find(Student.class, studentId) == null));

        em.close();
        factory.close();
    }
}

factory → entity manager → transaction

  • EntityManagerFactory: expensive, thread-safe application-level object. Create once for a persistence unit and close at shutdown.
  • EntityManager: owns a persistence context that tracks managed objects. Keep it short-lived, close it, and never share it between threads.
  • EntityTransaction: begin() starts a unit of work, commit() flushes pending changes and commits, and rollback() cancels database changes in the active transaction.

For example, two inserts inside one transaction either commit together or are rolled back together. SQL can execute before commit, especially with identity-generated IDs; flush() sends pending SQL but does not commit the transaction. A later rollback can still undo those writes.

The reads here use find() without locking and are allowed outside a transaction in this setup. Writes require an active transaction. On the successful path, the example closes the entity manager and factory at the end. Handling failures and ensuring cleanup will be added when introducing exception handling. Rollback does not reset your Java objects to their previous field values.

🧷 remember
A new object is transient; persist() makes it managed; clear() or closing the entity manager makes it detached. Changing a managed entity inside a transaction is enough for an update. merge() returns a managed copy of detached state; the original object remains detached.

relationships: department and students

The snippets below extend the working example; they are not replacement files. Add the imports for OneToMany, ManyToOne, FetchType, JoinColumn, List, and ArrayList as needed. Put Department in its own file in com.example.jpa, give it a public or protected no-argument constructor, and register com.example.jpa.Department in persistence.xml. Add the department field to the existing Student class, preserving its ID and other fields.

@Entity
public class Department {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    private String name;

    @OneToMany(mappedBy = "department")
    private List<Student> students = new ArrayList<>();
}

@Entity
public class Student {
    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "department_id")
    private Department department;
}

The foreign key belongs on the student table. mappedBy says the student owns the database relationship. Keep both sides synchronized in helper methods when changing the relationship in memory.

lazy versus eager

  • LAZY: load the relationship when code first needs it. Usually safer for large collections.
  • EAGER: load the relationship immediately. Convenient, but can load much more data than the request needs.

Choose fetching deliberately. A relationship annotation is not a license to load the entire object graph.

entitymanager basics

entityManager.persist(student); // make managed; INSERT may occur before flush
entityManager.find(Student.class, id); // SELECT by id
entityManager.merge(student); // copy detached state
entityManager.remove(student); // DELETE managed entity

These operations usually run inside a transaction. The persistence context tracks managed objects and synchronizes changes with the database.

practice mini project: student department directory

Build a Java console application using JPA, Hibernate, and MySQL that manages students and their departments. Use exactly two tables: departments and students. A department can have many students, and every student must belong to one department.

Register both entity classes in persistence.xml. Keep the existing create-drop setting for this disposable exercise; inspect data while the application is still running, before closing the factory.

⚠️ gotcha
NOT NULL rejects missing values, but allows an empty string. Reject blank names and emails in your Java code as well. A student's name does not need to be unique; two students can share a name, but not an email address.

3. use joins to build reports

Run the following SQL in MySQL Workbench after inserting the sample data. An INNER JOIN returns matching student–department pairs:

SELECT s.name AS student_name, s.email, d.name AS department_name
FROM students s
INNER JOIN departments d ON s.department_id = d.id
ORDER BY s.name;

Expected: three rows — Asha and Ravi in Computer Science, and Meera in Electronics.

A LEFT JOIN keeps every department, including a department with no students:

SELECT d.name AS department_name, COUNT(s.id) AS student_count
FROM departments d
LEFT JOIN students s ON s.department_id = d.id
GROUP BY d.id, d.name
ORDER BY d.name;

Expected: Computer Science → 2, Electronics → 1, Mechanical → 0. Use COUNT(s.id) rather than COUNT(*) so an empty department counts as zero.

Your tasks: write a query that lists students from a department chosen by name, and another that lists only departments with no students. Then implement the first report in Java using JPQL:

SELECT s.name, s.email, d.name
FROM Student s JOIN s.department d
ORDER BY s.name

JPQL uses entity names and Java fields; SQL uses table names and columns. Run this projection with em.createQuery(jpql, Object[].class).getResultList() and print each row. For a department filter, bind the name with :departmentName and setParameter().

4. add update and delete operations

  1. Change Ravi's email and verify the new value with a fresh database read.
  2. Move Meera from Electronics to Computer Science by changing her department. If you keep both sides of the relationship in memory, update the collections too.
  3. Run the count report again: Computer Science should have 3 students, Electronics 0, and Mechanical 0.
  4. Delete Ravi, then verify that the student count is 2 and his department still exists.

Give each update or delete operation a transaction. Do not cascade deletion from a student to its department.

5. check that constraints actually work

Try each invalid operation separately in Workbench against the populated tables. Record the error and confirm that the invalid row or change was rejected.

  • UNIQUE: insert another student using Asha's email, then try a second department named Computer Science.
  • NOT NULL: insert a student with a NULL name or email, then try one without a department.
  • FOREIGN KEY: insert a student with a department ID that does not exist.
  • Referential integrity: try deleting Computer Science while students still reference it. Keep the foreign key's default restrictive delete behavior so MySQL rejects this operation.
  • Valid duplicate: insert another student named Asha with a different email and a valid department. This should succeed.
