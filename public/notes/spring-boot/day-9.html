the gateway is the front door; resilience and observability tell us what happens behind it.

today's outcome

Route client traffic through Spring Cloud Gateway and understand predicates, filters, logical service routes, timeouts, retries, circuit breakers, and health endpoints.

gateway architecture

Client
  ↓
API Gateway
  ├── /api/products/** → PRODUCT-SERVICE
  ├── /api/orders/**   → ORDER-SERVICE
  └── /api/users/**    → USER-SERVICE

Centralizing routing can also centralize cross-cutting concerns such as authentication, headers, metrics, and rate limits. It should not become a place where all business logic accumulates.

resilience vocabulary

  • Timeout: stop waiting after a bounded period.
  • Retry: try again for failures that are safe and likely temporary.
  • Circuit breaker: stop sending traffic to a failing dependency for a period.
  • Fallback: return a useful degraded response when the dependency is unavailable.
Closed → requests flow normally
Open → requests fail fast
Half-open → probe whether recovery happened
⚠️ gotcha
Retries can multiply traffic and duplicate writes. Retry only operations with a safe idempotency strategy.

observability basics

When a request crosses services, logs from one process are not enough. Add:

  • Logs: what happened.
  • Metrics: how often and how slowly it happens.
  • Traces: where time was spent across services.
  • Correlation IDs: which logs belong to one request.

Add Spring Boot Actuator and inspect /actuator/health. The official Actuator documentation explains endpoints and exposure settings.

practice

  1. Route product and order requests through a gateway.
  2. Add a request correlation ID to logs.
  3. Simulate a slow dependency and define a timeout and fallback policy.
