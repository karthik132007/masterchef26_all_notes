microservices solve organizational and scaling problems, while introducing distributed-systems problems.

today's outcome

Understand when a monolith is useful, what changes when services are split, and how service boundaries affect data, failures, and deployment.

start with the monolith

One application
  ├── student module
  ├── course module
  ├── payment module
  └── notification module

One deployment · often one database

A modular monolith can be an excellent starting point: simple local calls, simple transactions, and one deployment.

then split deliberately

Student Service       Product Service
      │                     │
      └──── HTTP calls ─────┘

Each service can have its own deployment and data ownership.
  • Benefits: independent deployment, team ownership, targeted scaling, and failure isolation.
  • Costs: network failures, latency, distributed debugging, data consistency, and operational complexity.
⚠️ architecture warning
Microservices are not automatically better. A badly split system can become a distributed monolith with more failure modes and no real independence.

service boundaries

Choose boundaries around business capabilities and ownership, not around every Java class. A service should own its data and expose a stable contract.

QuestionGood signal
Who owns this data?One service is responsible for writes and rules.
How often does it change?Related concepts change and deploy together.
What happens when it is unavailable?The caller has a timeout, fallback, or explicit failure path.

Start with a fixed URL to make the network boundary visible. Then ask: what happens when there are ten product instances, or the port changes?

distributed request checklist

  • Set a connection timeout and a response timeout.
  • Use an idempotent request when retries are possible.
  • Propagate a correlation ID for debugging.
  • Decide whether failure should be retried, cached, or returned immediately.
  • Do not pretend two service-local transactions are one global transaction.

official reading

Use the official Spring microservices page as a map of Spring Cloud capabilities. Treat it as a toolbox, not a requirement to adopt every component.

practice

  1. Split a simple classroom domain into Student Service and Course Service on paper.
  2. Write the endpoint contract for one cross-service call.
  3. Run two local instances of the same service on different ports and list what must change to call them.
